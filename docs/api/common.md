# API 공통 규칙

> 적용 범위: 병원용 API와 환자용 API 전체

## 1. 기본 경계

- API 버전 접두사는 `/api/v1`을 사용한다.
- 병원 직원과 환자는 인증 체계를 공유하지 않는다.
- 서버는 클라이언트가 전달한 병원 식별자를 신뢰하지 않고 인증 주체의 소속과 리소스 소유권을 검증한다.
- 실제 환자정보와 운영용 비밀번호·JWT·OTP·환자 링크 토큰을 코드, 테스트, 로그, 커밋에 남기지 않는다.

## 2. 인증 주체

| 구분 | 인증 방식 | 주요 권한 경계 |
|---|---|---|
| 병원 직원 | 직원 로그인·JWT·서버 RBAC | 병원 범위, 직원 역할, 환자·진료 소유권 |
| 환자 | 환자 링크·OTP·환자 세션 | 해당 환자의 승인 완료 데이터와 허용된 응답 기능 |

환자 인증에 직원용 JWT를 재사용하지 않는다. 세부 계약은 [병원용 API](hospital.md)와 [환자용 API](patient.md)에서 각각 관리한다.

## 3. 공통 보안 규칙

- 타 병원 리소스는 존재 여부를 노출하지 않도록 계약에서 정한 `404` 응답을 사용한다.
- 비밀번호·JWT·OTP·환자 링크 토큰 등 인증정보를 쿼리스트링으로 전달하지 않는다.
- URL에 포함될 수밖에 없는 일회성 환자 링크 식별값은 재사용을 제한하고 access log에 원문을 남기지 않는다.
- 오류 응답과 애플리케이션 로그·access log에는 민감정보 원문을 포함하지 않는다.
- 승인 전 안내, 미확정 OCR 결과와 원본 의료문서는 환자 API에 제공하지 않는다.

## 4. 공통 식별자와 영역 간 계약

| 항목 | 원칙 |
|---|---|
| `patient_id` | 병원 내부 환자 식별자. 외부에서 병원 범위를 지정하는 용도로 사용하지 않음 |
| `visit_id` | OCR·안내 승인·환자 링크·D+7 응답을 연결하는 진료 식별자 |
| 승인 안내 | 승인 완료 상태만 환자 조회와 챗봇 컨텍스트에 제공 |
| D+7 응답 | 해당 환자 세션과 `visit_id`에 연결해 저장하고 병원 화면에서 조회 |

필드 타입과 병원 업무의 상세 오류 계약은 [병원용 API](hospital.md)에서 관리한다.

## 5. 오류와 변경 관리

- 새로 추가하거나 변경하는 오류 `code`는 병원용과 환자용 모두 `UPPER_SNAKE_CASE`로 작성한다.
- 직원 인증의 기존 `invalid_credentials`, `token_expired`, `password_change_required`, `invalid_request`는 현재 코드·프런트 호환을 위해 예외로 유지한다. 별도 계약 변경 없이 문서만 대문자로 바꾸지 않는다.
- 도메인 규칙 위반은 `400`, 요청 스키마·필드 형식 검증 실패는 `422`로 구분한다. 인증·권한·충돌·리소스 오류는 각 계약의 HTTP 상태를 따른다.
- 도메인 오류는 코드와 사용자에게 표시할 메시지를 분리하고, 필드 오류가 있으면 공통 `field_errors` 구조를 사용한다.
- 엔드포인트·HTTP 메서드, 필수 요청·응답 필드, 인증·권한, 공통 오류 형식, 병원·환자 영역 간 계약의 변경은 구현 전에 팀에 공유한다.
- 합의되지 않은 API 범위 확장이나 별도 기능을 기존 Jira 일감에 추가하지 않는다.
- 동작에 영향이 없는 설명 보완도 PR에 변경 내용을 기록한다.
