# 프로젝트 개발 운영안

> 기술 리드 협의용 초안
> 기준일: 2026-08-18 / 기준 브랜치: `develop`

## 1. 목적

PCOS·자궁내막증 환자 교육용 웹서비스 MVP를 5명이 매 스프린트 공동 구현하기 위한 작업 원칙과 큰 일감 배분을 정한다.

- 메인 오너는 의사결정 정리와 완료 기준 확인을 맡는다.
- 구현은 직무 경계로 고정하지 않고, 모든 팀원이 매 스프린트 개발·검증·문서화에 참여한다.
- 의료 안전과 개인정보 보호는 부가 기능이 아니라 MVP 완료 조건으로 관리한다.
- 세부 티켓은 스프린트 시작 시 API·화면·검증 단위로 나누고 담당자와 리뷰어를 각각 지정한다.

## 2. 현재 MVP 경계

### 반드시 완성할 사용자 흐름

```text
병원 로그인
→ 환자·진료 건 등록
→ EMR·처방전·약봉투 업로드 및 OCR
→ 환자정보 일치 확인과 OCR 수정·확정
→ 승인 지식 기반 안내 생성 및 안전 검증
→ 의사 검토·승인
→ 원본 삭제 확인 후 링크 발송
→ 환자 OTP 인증
→ 복약안내·생활관리·챗봇 이용
→ D+7 복약·통증 확인
```

### 범위 조정

- 검사결과지는 OCR 업로드·추출 대상에서 제외한다.
- 환자 목표와 검사 목표 관리는 `가능하면` 범위로 둔다.
- 의료문서 원본 삭제, 역할 기반 접근통제, 토큰 비노출, 감사로그, 생성 안전 검증은 MVP에 유지한다.
- 실제 SMS, 고급 알림, PDF 출력, 만족도·오류 신고 등은 핵심 흐름 완료 후 적용한다.

## 3. 기능 오너십과 협업 기준

스프린트는 팀 전체의 통합 목표를 관리하고, 실제 구현 책임은 화면과 기능의 성격이 유사한 단위로 나눈다. 각 기능 오너는 해당 영역의 화면, API, 데이터, 테스트를 연결하여 완료할 책임을 갖는다.

### 기능별 수직 소유권

| 기능 영역 | 주 담당 | 구현 범위 | 기본 리뷰어 |
|---|---|---|---|
| 환자·진료 관리 | 유가은 (`yugaeun821`) | 환자·진료 건 화면, CRUD API, 데이터 모델, 정상·예외 테스트 | 김고은 |
| 문서 업로드·OCR | 김고은 (`Gomin-art`) | 업로드·처리 상태 UI, 파일 API, OCR 구조화·확정, 실패·재처리 테스트 | 한금준 |
| 안내 생성·의사 승인 | 이희진 (`2heej`) | 생성·검토·반려·승인 화면, 상태 전이 API, 의료 안전 검증 | 한금준 |
| 환자 인증·모바일 안내 | 권일준 (`iljun-sys`) | 링크·OTP·세션 UI/API, 모바일 안내 화면, 만료·재인증 테스트 | 이희진 |
| 챗봇·D+7 | 한금준 (`Funital`) | 챗봇 UI/API, 승인 컨텍스트 처리, D+7 입력·조회, 통합 테스트 | 김고은 |

주 담당은 해당 영역을 혼자 구현한다는 뜻이 아니다. API 계약과 완료 조건을 관리하고 병합 가능한 상태까지 연결하는 역할이며, 필요 시 기능 간 페어 작업으로 구현한다.

### 공통 모듈 오너십

| 공통 영역 | 메인 오너 | 협업 범위 |
|---|---|---|
| 기술 구조·통합·CI/CD | 한금준 | 모듈 경계, 공통 설정, 코드리뷰, 배포 구조 |
| API·DB·비동기 처리·AI 연동 | 김고은 | 공통 스키마, Redis·Worker, 외부 API 클라이언트 |
| 의료 안전·요구사항 | 이희진 | 금지 응답, 처방 외 약물 차단, 인수조건, 콘텐츠 검수 |
| UX/UI 일관성 | 권일준 | 사용자 흐름, 공통 컴포넌트, 접근성, 오류 상태 |
| QA 기준·회귀 관리 | 유가은 | 테스트 양식, 샘플 데이터, 결함 재현, 통합·회귀 확인 |

OCR·LLM/RAG·인증·권한·감사로그처럼 여러 기능에서 사용하는 코드는 공통 모듈로 한 번만 구현한다. 기능 오너는 합의된 인터페이스를 사용하고 공통 모듈을 임의로 복제하지 않는다.

### 리뷰 원칙

- 모든 기능 PR은 작성자가 아닌 기본 리뷰어가 검토한다.
- 의료 안전·개인정보 처리 변경은 이희진이 추가 검토한다.
- 인증·권한·비동기 처리·공통 구조 변경은 한금준이 추가 검토한다.
- 데이터 모델·외부 AI/OCR 연동 변경은 김고은이 추가 검토한다.
- 화면·사용성 변경은 권일준이, 테스트·예외 흐름은 유가은이 교차 확인한다.

## 5. 티켓과 GitHub 운영

### 일감 구조

```text
Sprint 목표
└─ 큰 일감(Epic 또는 상위 작업)
   ├─ FE 작업
   ├─ BE·AI 작업
   ├─ 테스트·데이터 작업
   └─ 문서·검수 작업
```

- 티켓 하나는 가능하면 0.5~2일 안에 검토 가능한 크기로 나눈다.
- 모든 티켓에 담당자, 리뷰어, 인수조건, 관련 화면/API를 기록한다.
- Jira-GitHub 연결 전 생성한 일감도 이후 이슈 키를 브랜치·커밋·PR에 추가하여 연결할 수 있다.
- 상태는 `할 일 → 진행 중 → 리뷰 → 검증 → 완료`로 통일한다.
- 막힘은 개인이 보유하지 않고 당일 공유해 페어 작업 또는 범위 조정으로 해결한다.

### Git 흐름

```text
origin/develop 최신화
→ 작업 브랜치 생성
→ 작은 단위 커밋
→ develop 대상 Draft PR
→ CI 및 동료 리뷰
→ 검증 완료 후 병합
```

- `main`: 배포 가능한 버전
- `develop`: 스프린트 통합 브랜치
- 작업 브랜치: `feat/*`, `fix/*`, `docs/*` 등 목적별 사용
- 기능 PR은 작성자 외 최소 1명이 리뷰한다.
- 인증·권한·삭제·LLM 안전 검증 변경은 기술 리드와 해당 인수조건 담당자가 함께 확인한다.

## 6. 완료 정의(Definition of Done)

다음 항목을 모두 만족해야 일감을 완료로 변경한다.

- 인수조건과 정상·예외 흐름이 확인되었다.
- 역할·소유권 검증이 서버에서 수행된다.
- 민감정보와 링크 토큰 원문이 화면·로그에 노출되지 않는다.
- 관련 테스트와 기존 핵심 흐름 회귀 테스트가 통과했다.
- 오류 처리와 감사로그가 필요한 행위에 반영되었다.
- PR 리뷰 의견을 처리하고 관련 문서를 갱신했다.
- 데모 범위를 벗어난 부분은 제한사항으로 명시했다.

## 7. 기술 리드와 우선 합의할 항목

1. 프론트엔드 저장 위치와 API 계약 공유 방식
2. Redis 작업 상태·재시도·실패 큐의 최소 구현 수준
3. 원본 파일 삭제 성공을 검증하고 발송을 해제하는 트랜잭션 경계
4. LLM 생성 전·후 안전 검증의 담당 모듈과 차단 응답 형식
5. 감사로그 append-only 보장 방식과 MVP 조회 범위
6. 로컬 모의 서비스와 실제 CLOVA·OpenAI·SMS 전환 기준
7. Sprint 6 배포 목표가 EC2 Compose인지 ECS 기반인지에 대한 최종 선택
8. PR 필수 리뷰어와 브랜치 보호 규칙 적용 시점

## 8. 스프린트 운영 리듬

- **시작:** 목표·티켓·인수조건 확인, 전원 일감 보유 여부 점검
- **매일:** 완료/오늘/막힘 공유, 필요 시 담당과 리뷰어 재배정
- **중간 점검:** 화면-API 연결과 예외 흐름을 통합 환경에서 확인
- **종료:** 데모, QA 결과, 미완료 사유, 다음 스프린트 이관 범위 확정

스프린트 종료 시 개인별 산출물 수보다 핵심 사용자 흐름의 실제 동작과 팀 공동 완료 여부를 우선한다.
