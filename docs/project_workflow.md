# 프로젝트 개발 운영안

> 기술 리드 협의용 초안
> 기준일: 2026-08-18 / 기준 브랜치: `develop`

## 1. 목적

PCOS·자궁내막증 환자 교육용 웹서비스 MVP를 5명이 매 스프린트 공동 구현하기 위한 작업 원칙과 큰 일감 배분을 정한다.

- 메인 오너는 의사결정 정리와 완료 기준 확인을 맡는다.
- 구현은 직무 경계로 고정하지 않고, 모든 팀원이 매 스프린트 개발·검증·문서화에 참여한다.
- 의료 안전과 개인정보 보호는 부가 기능이 아니라 MVP 완료 조건으로 관리한다.
- 세부 티켓은 스프린트 시작 시 API·화면·검증 단위로 나누고 담당자와 리뷰어를 각각 지정한다.

## 2. 현재 MVP 경계

### 반드시 완성할 사용자 흐름

```text
병원 로그인
→ 환자·진료 건 등록
→ EMR·처방전·약봉투 업로드 및 OCR
→ 환자정보 일치 확인과 OCR 수정·확정
→ 승인 지식 기반 안내 생성 및 안전 검증
→ 의사 검토·승인
→ 원본 삭제 확인 후 링크 발송
→ 환자 OTP 인증
→ 복약안내·생활관리·챗봇 이용
→ D+7 복약·통증 확인
```

### 범위 조정

- 검사결과지는 OCR 업로드·추출 대상에서 제외한다.
- 환자 목표와 검사 목표 관리는 `가능하면` 범위로 둔다.
- 의료문서 원본 삭제, 역할 기반 접근통제, 토큰 비노출, 감사로그, 생성 안전 검증은 MVP에 유지한다.
- 실제 SMS, 고급 알림, PDF 출력, 만족도·오류 신고 등은 핵심 흐름 완료 후 적용한다.

## 5. 티켓과 GitHub 운영

### 일감 구조

```text
Sprint 목표
└─ 큰 일감(Epic 또는 상위 작업)
   ├─ FE 작업
   ├─ BE·AI 작업
   ├─ 테스트·데이터 작업
   └─ 문서·검수 작업
```

- 티켓 하나는 가능하면 0.5~2일 안에 검토 가능한 크기로 나눈다.
- 모든 티켓에 담당자, 리뷰어, 인수조건, 관련 화면/API를 기록한다.
- Jira-GitHub 연결 전 생성한 일감도 이후 이슈 키를 브랜치·커밋·PR에 추가하여 연결할 수 있다.
- 상태는 `할 일 → 진행 중 → 리뷰 → 검증 → 완료`로 통일한다.
- 막힘은 개인이 보유하지 않고 당일 공유해 페어 작업 또는 범위 조정으로 해결한다.

### Git 흐름

```text
origin/develop 최신화
→ 작업 브랜치 생성
→ 작은 단위 커밋
→ develop 대상 Draft PR
→ CI 및 동료 리뷰
→ 검증 완료 후 병합
```

- `main`: 배포 가능한 버전
- `develop`: 스프린트 통합 브랜치
- 작업 브랜치: `feat/*`, `fix/*`, `docs/*` 등 목적별 사용
- 기능 PR은 작성자 외 최소 1명이 리뷰한다.
- 인증·권한·삭제·LLM 안전 검증 변경은 기술 리드와 해당 인수조건 담당자가 함께 확인한다.

## 6. 완료 정의(Definition of Done)

다음 항목을 모두 만족해야 일감을 완료로 변경한다.

- 인수조건과 정상·예외 흐름이 확인되었다.
- 역할·소유권 검증이 서버에서 수행된다.
- 민감정보와 링크 토큰 원문이 화면·로그에 노출되지 않는다.
- 관련 테스트와 기존 핵심 흐름 회귀 테스트가 통과했다.
- 오류 처리와 감사로그가 필요한 행위에 반영되었다.
- PR 리뷰 의견을 처리하고 관련 문서를 갱신했다.
- 데모 범위를 벗어난 부분은 제한사항으로 명시했다.

## 7. 기술 리드와 우선 합의할 항목

1. 프론트엔드 저장 위치와 API 계약 공유 방식

3. 원본 파일 삭제 성공을 검증하고 발송을 해제하는 트랜잭션 경계
4. LLM 생성 전·후 안전 검증의 담당 모듈과 차단 응답 형식
5. 감사로그 append-only 보장 방식과 MVP 조회 범위
6. 로컬 모의 서비스와 실제 CLOVA·OpenAI·SMS 전환 기준
7. Sprint 6 배포 목표가 EC2 Compose인지 ECS 기반인지에 대한 최종 선택
8. PR 필수 리뷰어와 브랜치 보호 규칙 적용 시점

## 8. 스프린트 운영 리듬

- **시작:** 목표·티켓·인수조건 확인, 전원 일감 보유 여부 점검
- **매일:** 완료/오늘/막힘 공유, 필요 시 담당과 리뷰어 재배정
- **중간 점검:** 화면-API 연결과 예외 흐름을 통합 환경에서 확인
- **종료:** 데모, QA 결과, 미완료 사유, 다음 스프린트 이관 범위 확정

스프린트 종료 시 개인별 산출물 수보다 핵심 사용자 흐름의 실제 동작과 팀 공동 완료 여부를 우선한다.
