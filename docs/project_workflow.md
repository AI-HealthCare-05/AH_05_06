# 프로젝트 개발 운영안

> 기술 리드 협의용 초안
> 기준일: 2026-08-18 / 기준 브랜치: `develop`

## 1. 목적

PCOS·자궁내막증 환자 교육용 웹서비스 MVP를 5명이 매 스프린트 공동 구현하기 위한 작업 원칙과 큰 일감 배분을 정한다.

- 메인 오너는 의사결정 정리와 완료 기준 확인을 맡는다.
- 구현은 직무 경계로 고정하지 않고, 모든 팀원이 매 스프린트 개발·검증·문서화에 참여한다.
- 의료 안전과 개인정보 보호는 부가 기능이 아니라 MVP 완료 조건으로 관리한다.
- 세부 티켓은 스프린트 시작 시 API·화면·검증 단위로 나누고 담당자와 리뷰어를 각각 지정한다.

## 2. 현재 MVP 경계

### 반드시 완성할 사용자 흐름

```text
병원 로그인
→ 환자·진료 건 등록
→ EMR·처방전·검사결과지·약봉투 업로드 및 OCR
→ 환자정보 일치 확인과 OCR 수정·확정
→ 승인 지식 기반 안내 생성 및 안전 검증
→ 의사 검토·승인
→ 원본 삭제 확인 후 링크 발송
→ 환자 OTP 인증
→ 복약안내·생활관리·챗봇 이용
→ D+7 복약·통증 확인
```

### 범위 조정

- 의료문서 원본 삭제, 역할 기반 접근통제, 토큰 비노출, 감사로그, 생성 안전 검증은 MVP에 유지한다.
- 실제 SMS, 고급 알림, PDF 출력, 만족도·오류 신고 등은 핵심 흐름 완료 후 적용한다.

## 3. 기능 오너십과 협업 기준

스프린트는 팀 전체의 통합 목표를 관리하고, 실제 구현 책임은 화면과 기능의 성격이 유사한 단위로 나눈다. 각 기능 오너는 해당 영역의 화면, API, 데이터, 테스트를 연결하여 완료할 책임을 갖는다.

### 기능 에픽과 수직 소유권

기능 에픽은 아래 구현 경계로 사용하고, 실제 작업은 확정된 담당 영역의 주 담당자와 리뷰어를 기준으로 배분한다.

| Jira | 기능 에픽 | 구현 범위 |
|---|---|---|
| `KEY-3` | 공통 인증·권한·관리자 기능 | 병원 로그인, JWT, 복수 역할, 서버 권한 검증, 관리자 추가 화면 |
| `KEY-1` | 환자·진료 건 관리 | 환자·진료 CRUD, 시간순 이력, D+7 응답 조회 |
| `KEY-2` | 의료문서 OCR·안내 생성·승인·챗봇 컨텍스트 | 문서 업로드부터 OCR 확정, 안내 생성·승인과 승인 데이터를 챗봇에 전달하는 계약까지의 핵심 흐름 |
| `KEY-4` | 환자 링크·OTP·모바일 안내·D+7 | 링크 수명주기, OTP·세션, 모바일 안내·챗봇 UI, D+7 입력 |
| `KEY-5` | 의료 안전·원본 삭제·감사로그 | 안전 차단, 원본 보관·삭제, 발송 차단, append-only 감사로그 |
| `KEY-6` | 배포·운영·통합 QA·데모 | AWS 기반, CI/CD, 모니터링, 통합·보안·성능 QA, 최종 시연 |

각 에픽의 주 담당은 해당 영역의 화면, API, 데이터, 테스트를 병합 가능한 상태까지 연결할 책임을 갖는다. 다른 구성원은 리뷰와 테스트에 참여하며, 세부 일감은 팀 전체가 매 스프린트 나누어 맡는다.

에픽 번호는 생성 순서이며 스프린트 순서를 의미하지 않는다. 기능 에픽의 작업·스토리를 실제 Sprint 2~7에 배치해 구현 순서를 관리한다.

### 구현 담당 영역

기능 에픽과 별개로 실제 구현 오너십은 다음 세 영역으로 묶는다. 주 담당은 혼자 모든 코드를 작성하는 사람이 아니라 해당 영역의 화면·API·데이터·테스트 연결과 최종 완료를 책임진다.

| 담당 영역 | 포함 범위 | 주요 에픽 | 주 담당 | 리뷰어 |
|---|---|---|---|---|
| 병원 공통·환자/진료 관리 | 병원 로그인, 인증·권한, 관리자 추가 화면, 환자·진료 건, 내부 알림 | `KEY-3`, `KEY-1` | 권일준 | 이희진 |
| 의료문서 OCR·안내 생성·승인 | EMR·처방전·검사결과지·약봉투 업로드, OCR 수정·확정, LLM 안내 생성, 의료 안전 검증, 의사 승인, 원본 삭제 연계 | `KEY-2`, `KEY-5` | 한금준 | 이희진 |
| 환자 인증·모바일·챗봇·D+7 | 링크·OTP·세션, 모바일 안내, 승인 데이터 기반 챗봇, D+7 입력 | `KEY-4`, `KEY-2`의 챗봇 연계 | 김고은 | 유가은 |

배포·공통 인프라·통합 QA는 세 영역 중 하나에 종속시키지 않고 `KEY-6`의 공동 작업으로 운영한다.

Sprint 2 초기 작업에서는 인증 API 계약·초기 설정을 이희진이, 합성데이터 시나리오·명세를 권일준이 맡는다. 이는 초기 일감의 교환 배정이며, 병원 공통·환자/진료 관리 영역의 주 담당과 리뷰어를 변경하지 않는다.

이희진은 서비스·의료 안전·요구사항 통합을 담당하고, 유가은은 QA·회귀 테스트 운영을 담당한다. 인증·인프라·AI 구조처럼 기술 위험이 큰 변경은 기술 리드 한금준이 영역 리뷰어와 함께 기술 검토를 지원한다. 모든 구성원은 주 담당 영역과 관계없이 매 스프린트 구현·검증·문서화 일감을 나누어 맡는다.

### 공통 모듈 오너십

| 공통 영역 | 오너 지정 기준 | 협업 범위 |
|---|---|---|
| 기술 구조·Redis·Worker·CI/CD | 기술 리드 협의 후 지정 | 모듈 경계, 비동기 작업 규칙, 공통 설정, 배포 구조 |
| OCR·안내 데이터 흐름 | 단일 주 담당 지정 | 문서 업로드 → OCR 확정 → 안내 생성·승인의 구현·데이터 계약·안전 검증 |
| 챗봇 연계 계약 | 환자 모바일·챗봇 담당 지정 | 승인 완료 데이터의 챗봇 컨텍스트 전달 계약과 환자 이용 흐름 검증 |
| 프롬프트·의료 안전·요구사항 | 의료 안전 검수 책임자 지정 | 금지 응답, 처방 외 약물 차단, 인수조건, 콘텐츠 검수 |
| UX/UI 일관성 | 권일준 | 사용자 흐름, 공통 컴포넌트, 접근성, 오류 상태 |
| QA 기준·회귀 관리 | QA 운영 책임자 지정 | 테스트 양식, 샘플 데이터, 결함 재현, 통합·회귀 확인 |

API·DB는 특정 공통 오너에게 몰아주지 않고 각 기능 담당자가 자신의 API, 데이터 모델, 마이그레이션, 테스트를 함께 구현한다. 공통 오너는 인터페이스와 구현 규칙을 관리하며 다른 담당자의 기능 코드를 대신 전담하지 않는다.

OCR·LLM/RAG·인증·권한·감사로그처럼 여러 기능에서 사용하는 코드는 공통 모듈로 한 번만 구현한다. 기능 오너는 합의된 인터페이스를 사용하고 공통 모듈을 임의로 복제하지 않는다.

Sprint 5의 화면 설계·UI/UX 고도화 작업은 권일준이 담당한다. 기능 구현 소유권은 그대로 유지하여 챗봇·환자 모바일은 김고은, OCR·안내 생성은 한금준이 이어서 담당하고, UI/UX 담당자는 기능 계약을 임의로 변경하지 않는다.

### OCR·안내와 챗봇의 경계

- 문서 업로드 → OCR 수정·확정 → 안내 생성·승인은 하나의 의료문서 처리 흐름으로 묶고 한 명의 주 담당자가 처음부터 끝까지 구현·통합한다.
- 챗봇은 승인 완료된 데이터를 입력으로 사용하는 별도의 환자 이용 흐름으로 보고, 환자 인증·모바일 안내·D+7 영역과 함께 담당한다.
- 두 영역은 `승인 완료된 구조화 데이터와 지식만 챗봇 컨텍스트로 제공한다`는 API·데이터 계약으로 연결한다.
- 각 주 담당자 외 구성원은 코드 리뷰와 정상·예외·의료 안전 테스트를 맡는다.
- 특정 담당자에게 작업량이 과도하게 집중되지 않도록 공통 UI, 테스트 데이터, 문서화, 회귀 테스트는 별도 하위 작업으로 나누어 공동 수행한다.
- 주 담당자와 리뷰어는 위 담당 영역 표를 따르며, 세부 티켓의 성격에 따라 추가 기술·의료·QA 리뷰어를 지정할 수 있다.

### 리뷰 원칙

- 모든 기능 PR은 작성자가 아닌 지정 리뷰어가 검토한다.
- 의료 안전·개인정보, 인증·권한·비동기 처리, 외부 AI/OCR, 화면·사용성, 테스트·예외 흐름의 필수 리뷰어는 담당자 확정 시 함께 지정한다.
- OCR·안내 및 챗봇 영역의 리뷰어는 구현을 분할 소유하지 않고 코드 리뷰와 테스트를 통해 구조와 데이터 흐름을 확인한다.

## 5. 티켓과 GitHub 운영

### 일감 구조

```text
기능 영역(Epic)
└─ 작업/스토리
   ├─ FE 작업
   ├─ BE·AI 작업
   ├─ 테스트·데이터 작업
   └─ 문서·검수 작업
```

- 티켓 하나는 가능하면 0.5~2일 안에 검토 가능한 크기로 나눈다.
- 모든 티켓에 담당자, 리뷰어, 인수조건, 관련 화면/API를 기록한다.
- Jira-GitHub 연결 전 생성한 일감도 이후 이슈 키를 브랜치·커밋·PR에 추가하여 연결할 수 있다.
- 기본 상태 흐름은 `할 일 → 진행 중 → 리뷰 → 완료`로 운영하며, 필요한 작업만 `리뷰 → QA → 완료`를 거친다.
- 브랜치 생성 시 `진행 중`, PR 생성 시 `리뷰`로 자동 전환한다. PR 병합 시 `qa-required` 라벨이 있으면 `QA`, 없으면 `완료`로 자동 전환한다.
- 인증·권한·OTP, 개인정보·원본 삭제·감사로그, OCR·LLM 의료 안전, 영역 간 통합, 회귀 위험이 큰 버그는 `qa-required` 적용을 우선 검토한다.
- QA는 리뷰를 반복하지 않고 병합 후 통합 환경의 핵심 회귀·권한·보안 시나리오만 확인한다. QA 확인 후 `완료`는 수동 처리한다.
- 브랜치명·커밋·PR 제목 또는 본문에 Jira 키(`KEY-번호`)를 포함한다.
- 막힘은 개인이 보유하지 않고 당일 공유해 페어 작업 또는 범위 조정으로 해결한다.

### Jira 일감 생성 권한

- 합의된 에픽·기능 범위 안의 작업·스토리·하위 작업·버그는 발견한 팀원이 직접 생성할 수 있다.
- 새 기능·에픽, MVP 범위·우선순위 변경, 의료 안전·보안·개인정보 정책 변경, 여러 영역에 영향을 주는 API 계약 변경은 생성 전에 이희진과 합의한다.
- 생성 전 중복 일감을 검색하고 올바른 상위 에픽 또는 작업에 연결한다.
- 일감에는 목적·범위·인수조건, 관련 화면/API, 담당자·리뷰어, 우선순위, 스프린트 또는 백로그 위치를 기록한다.
- 보고자는 일감을 제기하거나 생성한 사람으로 유지하며 리뷰어 대신 사용하지 않는다.
- AI 작업 중 추가 구현이 필요해지면 먼저 Jira 일감을 생성하거나 기존 일감의 범위를 갱신한 뒤 구현한다.

`KEY-번호 작업 시작해줘`는 구현 시작 의사로 간주한다. AI가 Jira 쓰기 권한을 보유하고 해당 일감이 `할 일`이면 `진행 중`으로 전환한다. 접근 또는 전환에 실패하면 수동 변경이 필요함을 알린다. 브랜치 생성 자동화가 같은 전환을 다시 감지해도 상태를 되돌리지 않으므로 충돌하지 않는다.

### AI 기반 작업 단위

팀원이 AI 도구를 사용하더라도 작업 계약과 검수 책임은 Jira 담당자에게 있다. 작업 추적이 분산되지 않도록 GitHub Issue를 중복 생성하지 않고 Jira를 기준으로 운영한다.

```text
Jira 하위 작업 1개
→ AI 작업 대화 1개
→ 작업 브랜치 1개
→ Draft PR 1개
→ 사람 또는 별도 검수 AI의 리뷰
→ 병합 후 완료 또는 필요 시 QA
```

- AI는 Jira에서 작업 범위, 관련 화면·API, 인수조건, 테스트, 변경 금지 범위를 읽는다. Jira에 접근할 수 없을 때만 사용자가 일감 링크나 설명을 제공한다.
- AI가 Jira에 없는 요구사항을 임의로 추가하거나 공통 모듈을 복제하지 않도록 한다.
- 구현 AI와 검수 AI를 가능하면 분리하고, 같은 결과를 작성자의 자체 판단만으로 승인하지 않는다.
- 작업 중 범위가 달라지면 먼저 Jira 설명과 인수조건을 갱신한 뒤 구현을 계속한다.
- PR에는 AI 사용 여부보다 실제 변경 범위, 테스트 결과, 제한사항을 정확히 기록한다.

### Git 흐름

```text
origin/develop 최신화
→ Jira 키를 포함한 작업 브랜치 생성
→ 작은 단위 커밋
→ develop 대상 Draft PR
→ CI 및 동료 리뷰
→ 검증 완료 후 병합
```

- `main`: 배포 가능한 버전
- `develop`: 스프린트 통합 브랜치
- 작업 브랜치: `feat/KEY-50-patient-history`, `fix/KEY-61-ocr-permission`, `docs/KEY-번호-설명` 형식으로 Jira 키와 목적을 포함한다.
- 기능 PR은 작성자 외 최소 1명이 리뷰한다.
- 인증·권한·삭제·LLM 안전 검증 변경은 기술 리드와 해당 인수조건 담당자가 함께 확인한다.

### 커밋 규칙

커밋 제목은 다음 형식을 사용한다.

```text
<이모지> <타입>: [KEY-번호] 변경 요약
```

예시:

```text
✨ feat: [KEY-50] 환자 상세 조회 화면 구현
🐛 fix: [KEY-61] OCR 타 병원 접근 차단
✅ test: [KEY-67] 미확정 OCR 사용 차단 테스트 추가
📝 docs: [KEY-37] Sprint 2 검수 절차 정리
```

- 이모지와 타입은 한금준이 작성한 `.github/commit_template.txt`를 기준으로 사용한다.
- 커밋 하나에는 한 가지 논리적 변경만 담고, 여러 Jira 일감을 한 커밋에 섞지 않는다.
- `WIP`, `수정`, `작업함`처럼 변경 목적을 알 수 없는 메시지는 사용하지 않는다.
- 커밋 본문에는 필요한 경우 무엇을 변경했는지와 왜 변경했는지, 제한사항을 기록한다.
- 커밋 전 `git diff`로 변경 범위를 확인하고 관련 테스트·포맷·민감정보 노출 여부를 점검한다.
- 실제 환자정보, 비밀번호, API 키, JWT·OTP·환자 링크 토큰, 운영 환경변수는 커밋하지 않는다.
- AI가 생성한 코드도 담당자가 diff와 테스트 결과를 확인한 뒤 커밋한다.

### PR과 Jira 연결 규칙

- PR 제목은 `[KEY-번호] 변경 요약` 형식으로 작성하고 기본 대상 브랜치는 `develop`으로 한다.
- PR 본문에 Jira 링크, 변경 범위, 테스트 결과, 화면 또는 API 영향, 남은 제한사항을 기록한다.
- 하나의 PR은 원칙적으로 하나의 Jira 하위 작업만 해결한다. 공통 변경으로 여러 일감이 연결될 때는 주 Jira 키와 영향받는 키를 구분한다.
- Draft PR을 일찍 열어 충돌과 API 계약 차이를 확인하고, 리뷰 준비가 끝나면 Ready로 전환한다.
- PR 생성 시 Jira 상태는 `리뷰`로 전환한다. 리뷰어는 코드리뷰, 기능 시연, 인수조건을 확인한 뒤 병합한다.
- PR 병합 시 `qa-required` 라벨이 있는 일감만 `QA`로 전환하고, 나머지는 `완료`로 전환한다. 자동화 실패 시 담당자가 수동으로 바로잡는다.
- `qa-required` 일감은 QA 담당자가 병합 후 통합 환경의 핵심 회귀·권한·보안 결과를 확인한 뒤 `완료`로 변경한다.

## 6. 완료 정의(Definition of Done)

다음 항목을 모두 만족해야 일감을 완료로 변경한다.

- 인수조건과 정상·예외 흐름이 확인되었다.
- 역할·소유권 검증이 서버에서 수행된다.
- 민감정보와 링크 토큰 원문이 화면·로그에 노출되지 않는다.
- 관련 테스트와 기존 핵심 흐름 회귀 테스트가 통과했다.
- 오류 처리와 감사로그가 필요한 행위에 반영되었다.
- PR 리뷰 의견을 처리하고 관련 문서를 갱신했다.
- 데모 범위를 벗어난 부분은 제한사항으로 명시했다.

## 8. 스프린트 운영 리듬

- **시작:** 목표·티켓·인수조건 확인, 전원 일감 보유 여부 점검
- **매일:** 완료/오늘/막힘 공유, 필요 시 담당과 리뷰어 재배정
- **중간 점검:** 화면-API 연결과 예외 흐름을 통합 환경에서 확인
- **종료:** 데모, QA 결과, 미완료 사유, 다음 스프린트 이관 범위 확정

스프린트 종료 시 개인별 산출물 수보다 핵심 사용자 흐름의 실제 동작과 팀 공동 완료 여부를 우선한다.
