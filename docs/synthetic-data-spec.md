# 합성 데이터 명세 — 환자 · 진료 · 처방 · 검사결과

> `KEY-13` · 하위 `KEY-27`(시나리오 매트릭스) · `KEY-30`(필드 매핑)
> 기준 — 와이어프레임 v2.3.1 (64프레임) · 2026-08-19

개발 · 데모 · QA에서 **실제 환자정보를 한 건도 쓰지 않기 위한** 규격이다.
FE · BE · OCR · LLM · QA가 **같은 시나리오 ID로 같은 데이터를 부른다.**

---

## 1. 절대 규칙

| | |
|---|---|
| **실제 환자 데이터 금지** | 원본은 물론이고 **실환자를 변형한 값도 쓰지 않는다.** 이름 · 생년월일 · 전화번호 · 차트번호 전부 지어낸 것이다 |
| **실제 연락처 금지** | 휴대폰은 `010-XXXX-XXXX` 꼴이되 실제로 존재할 수 있는 번호다 — **문자 발송 대상에 절대 넣지 않는다.** 개발·테스트 환경은 발송을 콘솔 출력으로 대체한다 |
| **출처 표기** | 검사 수치와 안내 문구는 식약처 의약품정보와 원장님 검수본에서 왔다. 임의로 만들지 않는다 |
| **한 곳에서만 고친다** | 데이터의 정본은 `docs/data/synthetic-patients.csv` 하나다. 코드에 값을 박지 않는다 |

## 2. 시나리오 ID

```
SYN-{질환}-{번호}

  SYN-EMS-01 ~ 10    자궁내막증        비잔
  SYN-PCOS-01 ~ 09   다낭성난소증후군   야즈 · 메트포르민
  SYN-BOTH-01        두 질환 동시
  SYN-DUP-01 ~ 03    동명이인 세 명     검색·선택 화면용
  SYN-CHK-01 ~ 05    확인 문자 응답 5종  (환자가 아니라 응답이다)
```

**이 ID가 팀 공용 이름이다.** 티켓 · 테스트 · 픽스처 · 버그 리포트에서 이 ID로 부른다.
차트번호(`12401`)는 화면에 보이는 값이고, 시나리오 ID는 **팀이 서로에게 쓰는 값**이다.

### 동명이인 — 등록 화면(`S1-2`)의 핵심 위험

`S1-2`는 검색 결과에서 **엉뚱한 사람을 고르면 안 되는** 화면이다. 그래서 **같은 이름 세 명**을 따로 둔다.

| ID | 이름 | 생년월일 | 차트 | 이번 진료 |
|---|---|---|---|---|
| `SYN-DUP-01` | 김서연 | 1975-03-09 | 08123 | 없음 — **환자 레코드만** |
| `SYN-DUP-02` | 김서연 | 1988-07-14 | 10771 | 없음 — **환자 레코드만** |
| **`SYN-DUP-03`** | **김서연** | **1990-01-01** | **12345** | 자궁내막증 · 비잔 84일 |

「김서연」으로 검색하면 셋이 다 뜨고, **생년월일로 갈라야** 고를 수 있다.
이름만으로는 못 고른다는 것이 이 화면의 요구사항이다.

`SYN-DUP-03`은 **환자 화면 디자인 목업이 쓰는 그 사람**이다 — 디자인 · 시드 · 데모가 같은 한 명을 본다.

## 7. 모자란 것 — 다음에 채운다

| 무엇 | 왜 필요한가 | 어떻게 |
|---|---|---|
| **`S1-8` 두 곳에 있음** | 같은 검사가 EMR과 검사지 양쪽에 **다른 값**으로 있을 때. 검사일이 최근인 쪽을 쓴다 | 기존 환자 하나에 **검사지 한 장을 덧붙여** 만든다 — 새 환자를 늘리지 않는다 |
| **`S1-10` 생성 실패** | 판독은 됐는데 조립이 실패한 상태. 나가는 길 셋이 다 살아 있는지 봐야 한다 | 데이터가 아니라 **주입 실패**로 만든다 — 시드가 아니라 테스트 더블의 몫 |
| **저신뢰 값** | 티켓의 「저신뢰」 케이스. OCR 신뢰도가 낮아 사람이 확인해야 하는 값 | OCR 결과에 신뢰도 칸이 생긴 뒤 (`KEY-2` 영역) |

**`S1-10`과 저신뢰는 환자 데이터로 만들 수 없다** — 처리 과정의 실패라 픽스처가 아니라 **테스트 더블**이 맡는다. `KEY-14` 시드 스크립트 범위 밖이다.

### ⚠ 이 절은 아직 반쪽이다

`KEY-30`의 완료 조건은 **「필드명과 타입이 API 계약과 일치」**인데, **지금 API 계약을 확인할 수 없다.**

- 티켓이 가리키는 노션 문서(`app.notion.com/p/766a59d4…`)에 **접근이 안 된다**
- 워크스페이스의 「API 명세서」는 **스텁 상태**다 — 본문에 「현재 스텁 상태(템플릿 예시 1건)」라고 적혀 있고, 인라인 DB의 `Domain` 선택지가 `Community · Subject · QnA · Test · CourseGeneration…`으로 **다른 프로젝트 템플릿 그대로**다

**위 표는 ERD(`spec-medical.md` 22표) 기준이다.** API 요청·응답 필드명은 `KEY-12`(환자·진료 모델 v1 동결 · 김고은)가 끝난 뒤 별도 브랜치에서 채운다.

## 9. 적재 규칙 (`KEY-14`에 넘기는 것)

| | |
|---|---|
| 고정 시드 | 같은 명령이 **같은 결과**를 낸다. uuid는 시나리오 ID에서 결정적으로 만든다 |
| 선택 적재 | `빈 상태` · `정상만` · `전체`를 골라 넣을 수 있다 — `S1-1`을 보려면 아무것도 안 넣는다 |
| 중복 처리 | 다시 돌려도 쌓이지 않는다. 차트번호가 자연키다 |
| 데모 ≠ 테스트 | 데모용은 `SYN-EMS-01` · `SYN-PCOS-01` 둘이면 충분하다. 예외 케이스는 테스트에서만 |
| 발송 금지 | **적재된 번호로 실제 문자를 보내지 않는다.** 개발·테스트 환경은 콘솔 출력으로 대체 |
