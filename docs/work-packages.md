## 0. 배분 원칙

- 묶음(WP) 1개 = 오너 1명 = 수직 슬라이스(화면 + API + 데이터 + 테스트). 계층(FE/BE) 분리 배정 안 함.
- 하위작업은 WP당 최대 3개. 기존처럼 결정·와이어링 티켓을 잘게 쪼개지 않는다.
- PR 단위 = 기능 수직, 프레임 ID(`S1-6`, `P7-3` 등) 기준. 대규모 일괄 병합 안 함 — 병합 주기를 짧게.
- 완료 = 테스트 통과가 아니라 화면 동작 확인(`?mock=1` 없이).
- 공통 인수조건(전 WP): DB 변경 시 Aerich migration 필수 · 깨끗한 DB와 기존 DB 모두 upgrade 성공 · 재실행 멱등 · 수동 SQL 금지 · downgrade·복구 절차 기록 · 실패 시 부분 성공으로 두지 않고 명확히 중단.

## 3. WP별 하위작업

### WP-A 로컬 부트스트랩·환경 재현 — 유가은 / 이희진 — KEY-228

근거: 한금준 개선안 §7.1과 PR #160. 현재 구현 일감은 KEY-228이며, 사용법 문서는 KEY-229, clean-clone CI 검증은 KEY-230으로 분리한다.

1. **Compose 로컬 변경** — PR #160에서 확정한 `web`/`ocr` 프로필을 유지하고 `minio-init`도 `ocr` 프로필의 일회성 도구로 추가, `fastapi`에 `./scripts:/app/scripts:ro`·`./docs/data:/app/docs/data:ro` 마운트(로컬 전용, 운영 이미지 미포함). 기존 `ai`/`tools` 초안은 별도 프로필로 늘리지 않고 `--with-ocr-worker` 한 옵션에 흡수한다.
2. **`scripts/bootstrap-local.sh`** — Docker·유효 포트 검사 → `.env` 생성·검증(`SECRET_KEY` 난수, MySQL·MinIO 로컬 비밀값 생성, 기존 `.env` 미덮어쓰기) → 의존 컨테이너 healthcheck 대기 → FastAPI HTTP 대기 → 컨테이너 내부 `aerich upgrade`(실패 시 중단) → 선택 시 `minio-init` 일회성 실행 → `seed.py --mode staff` → `check_schema_drift.py` → `smoke.py` health·auth·core. 멱등, 실패 단계와 해결 방법 출력.
3. **후속 범위** — `scripts/dev.sh`·`README.md`·`envs/example.local.env` 정리는 KEY-229, 깨끗한 환경 bootstrap CI 재현성 검증은 KEY-230에서 진행한다.

기본 bootstrap은 AI Worker·OCR E2E를 요구하지 않는다. OCR 흐름은 `--with-ocr-worker` / `dev.sh check-e2e` 선택 옵션.
최초 빌드 목표: AI Worker 제외 10분 이내. 5분은 사전 빌드 이미지 pull 시 적용(데모 안정화 후).

### WP-B 환자 진입 인증·OTP — 권일준 / 유가은 — KEY-212

이번 주 실제 부하는 **가볍다**. OTP를 고정 `000000` 검증으로만 간다. 그래서 권일준이 WP-S를 직접(온전히) 맡고 한금준은 WP-S 기술 리뷰만 본다.

1. 무인증 GET 경로 제거 + FE 6자리 입력·재발송 타이머를 실제 검증 API에 연결(`P1-2`).
2. OTP는 **고정 `000000` 검증만** 한다. 난수 생성·실제 SMS·발송 예약은 없다. mock 발송 어댑터는 **1개**("발송 성공" 상태 + 로그만). `MOCK_OTP_CODE`는 개발·로컬·테스트 한정이며, 운영에서는 설정돼도 우회가 동작하지 않는다 — KEY-200 시딩 게이트(환경변수 + 조건 이중 확인) 패턴 재사용.
3. **여기는 줄이지 않는다.** 두 단계로 나눈다.
   - **(9/2, KEY-212에 포함) 운영 OTP 우회 차단 확인** — `MOCK_OTP_CODE`가 설정돼도 실운영에서 우회가 안 되는 것을 테스트로 확인. 이걸 확인하지 않고 9/3 시연하지 않는다. KEY-212는 이 확인까지 완료하면 9/2 마감한다.
   - **(별도 후속 티켓) 추가 회귀** — 링크 유효성·만료·폐기 검사와 5회 실패 잠금(`OTP_LOCKED`/`Retry-After`), 토큰·인증번호 원문 미노출([`qa/KEY-48-log-masking-review.md`](qa/KEY-48-log-masking-review.md)). KEY-212 하위가 아니라 별도 티켓으로 빼서 데모 게이트 티켓을 깨끗하게 닫는다.

### WP-C 스탭 검토 → 의사 승인 → 환자 링크 — 김고은 / 이희진 — KEY-213

①·②는 9/3 데모 임계 경로라 **9/2까지**. ③은 데모 후 정리라 9/4.

1. **(9/2) 상태 전이**: 스탭 검토 → 의사 승인 요청 전이(별도 Submit API 필요 여부 먼저 조사), 의사 RBAC 승인, 반려(`APPROVAL_RETURNED`) → 재제출 전이 (B6).
2. **(9/2) 데모 링크 경로**: 의사 승인 직후 환자 링크 발급·화면 표시·복사([`qa/KEY-205-patient-link-launch.md`](qa/KEY-205-patient-link-launch.md)), 의료진 화면에 D+7 체크인 링크 노출 (B4), `POST /checkins/{token}/signals` 추가 또는 잘못된 FE 호출 제거 (B8 — 데모에 D+7 저장이 포함되므로 링크 연결과 함께 끝내야 함).
3. **(9/4) 안내 본문 연계 + 링크 수명주기**: 확정 시 `Prescription` 생성 → 처방별 주의·응급문구 8종 활성화, 안내 본문에 약품명·용량·횟수·일수 반영 및 `[합성]` 접두어 제거, 생성 실패 시 최소 재시도, 링크 유효기간 168h + 수동 재발급·폐기 (B5 최소). 발송·폐기 이력 모델(`SendLog` 계열)은 Sprint 5.

### WP-D OCR 판독 안정화 — 한금준 / 이희진 — KEY-214

1. **FE**: 확정 버튼 `{confirm: true}` 전송 연결 (B1, **P0 게이트** — 서버 변경 없음) + 항목 코드 → 한글 명칭 변환표(`MEDICATION_NAME` 노출 제거) + 복수 파일 업로드 시 파일별 작업 조회 (B7).
2. **BE**: 필수항목 게이트를 Phase 3(트랜잭션 저장) 이후로 이동, 미충족 시 처리 중단 대신 "확인 필요" 상태로 저장 → 기존 복구 UI(「직접 입력」)·`PATCH /ocr/fields/{id}` 활성화 (B2). 재시도·중복 실행 방지. 추출기 복수 약제(정규식 첫 매칭·표 파서 첫 행) 수정.
3. 고정 합성 fixture로 정상·저신뢰·실패·타임아웃 4상태 재현([`ocr-fixtures.md`](ocr-fixtures.md)) + `ai_worker` 추출기 테스트 15건 CI 편입 + 미확정 OCR의 안내 생성 차단 회귀.

## 6. 팀 진행 방식

1. PR 단위 = 기능 수직(화면 + API + 테스트), 프레임 ID 기준. 계층 분리·대규모 일괄 병합 금지 (진단 §5.3).
2. 완료 = 테스트 통과가 아니라 화면 동작 확인(`?mock=1` 없이).
3. 리뷰 SLA: PR ready 후 1영업일 내 첫 리뷰. 현재 정체 5건(#160·#165·#168·#169·#170)을 이번 주 해소.
4. 하루 공유: 완료 / 오늘 / 막힘 + WP 경계 충돌 즉시 신고. 권일준 3개 WP 부하 모니터링.
5. WP-A 서면 병행: 새 환경변수·migration·seed·smoke는 각 기능 PR에서 함께 갱신 (한금준 개선안 §9 체크리스트).
6. 시연 전 수동 확인(정적 분석 불가, 진단 §8): EC2 스키마 상태 · `OPENAI_API_KEY` 설정 여부 · `drug_caution_content` 시드 13행.
