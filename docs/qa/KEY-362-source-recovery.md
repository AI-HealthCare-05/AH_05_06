# KEY-362 원본 삭제 보류 복구

## 계약

- `HELD / SOURCE_NOT_DELETED`는 정상 삭제 대기가 아니라 복구가 필요한 예외다.
- 발송 예정 목록과 환자/의사 현황의 문자 상세에 안전한 실패 유형과 발생 시각을 표시한다.
- staff/doctor만 `POST /api/v1/messages/{id}/source-retry`를 요청할 수 있다. 타 병원은 404, admin 단독은 403.
- 본문은 `{ "generation": <조회 응답의 source_retry_generation> }`이다. 요청 즉시 발송하거나 상태를 변경하지 않는다.
- 기존 메시지의 복구 대기 플래그만 기록한다. 같은 세대의 요청은 실패 후 늦게 도착해도 다시 실행하지 않는다. 실패 후 새 요청은 새로 조회한 세대를 사용한다.
- 기존 발송 워커가 HELD 복구 요청도 claim한다. 다른 게이트를 통과한 뒤 원본 삭제, 물리 부재 확인, 삭제 기록/OCR raw_text 제거를 수행한다.
- 성공해야 SCHEDULED로 복귀한다. 다음 워커 주기에서 게이트를 다시 검사해 발송한다. 삭제·검증 실패 시 HELD 유지.
- 복구는 새 메시지/환자 링크를 만들지 않는다. 일반 FAILED 재발송 계약은 변경하지 않는다.

## 감사 및 보안

- SOURCE_RETRY: 요청자 내부 ID와 요청 세대.
- SOURCE_PURGED / SOURCE_ALREADY_PURGED: 문서 내부 ID만 기록. 물리 삭제와 DB 기록은 문서 잠금으로 직렬화하며 삭제 시각/OCR purge/이벤트를 같은 DB 트랜잭션에 기록한다.
- SOURCE_VERIFIED / SOURCE_REQUEUED: 검증 완료 후 복구 전이와 같은 트랜잭션.
- HELD: 고정된 사유/실패 유형만 기록. 예외 내용·파일 경로·환자 연락처는 기록하지 않는다.
- 기존 보류의 발생 시각은 migration 69가 기존 HELD 감사 이벤트에서만 가져온다. 과거 실패 유형이 없으면 추측하지 않고 기록 없음으로 표시한다.
- 워커 장애로 claim이 남은 건을 UI에서 강제로 해제하지 않는다. 공급자 접수 여부를 모르는 상태에서 재발송하면 중복 발송 위험이 있기 때문이다.

## 검증 시나리오

1. 정상 최초 발송: 자동 원본 삭제와 OCR purge 후 1회 발송.
2. 자동 삭제 실패: 백오프 재시도 소진 후 PURGE_RETRY_EXHAUSTED 보류.
3. 삭제 기록이 있는데 파일이 있는 경우: DELETION_RECORD_MISMATCH, 문자 미발송.
4. 삭제 재시도: 요청 직후 HELD 유지, 워커 검증 후 SCHEDULED, 이후 1회 발송.
5. 저장소 접근/삭제/부재 검증 실패: HELD 유지와 최신 시각/유형 갱신.
6. 동일 세대 중복·지연 요청, 동시 워커: 1회 복구 및 1회 발송.
7. 승인 취소/수신거부/다른 안전 게이트: 삭제·발송 우회 없음.
8. 권한·타 병원 차단, 목록/상세 동일 메타, 기존 일반 재발송 회귀.

배포 시 migration 69와 API·워커·프론트엔드를 함께 반영한다. 실제 발송 검증은 별도 승인된 합성 환자/수신 번호로 수행한다. KEY-5 영역이므로 한금준 기술 검토 및 qa-required 대상이다.
