# 프런트 수동 브라우저 확인 절차

> 기준일: 2026-08-26
> 담당: 권일준 · 리뷰어: 이희진
> 상위 에픽: KEY-6 · 근거 작업: KEY-182 (발견: KEY-129 / PR #131)
> 기준 자료: `frontend/tests/browser-shim.js`, `.github/PULL_REQUEST_TEMPLATE.md`

## 0. 이 문서가 있는 이유

`frontend/tests/browser-shim.js` 는 **일부러** 화면을 안 그린다. 껍데기 요소에
`innerHTML`·`textContent`·`value` 를 넣으려 하면 그 자리에서 던진다.

> 화면을 그리는 함수를 검사에서 부르면 조용히 통과하는 대신 그 자리에서 죽는다 —
> 「검사가 화면까지 본다」는 착각이 제일 비싸다. 화면은 브라우저에서 눈으로 본다.
> — `browser-shim.js`

이 결정 자체는 옳다. 브라우저를 흉내 내기 시작하면 껍데기가 끝없이 자란다.
다만 그 대가로 **자동 검사가 못 보는 구간**이 생기고, 지금까지는 그 구간을
리뷰어가 그때그때 눈으로 보고 코멘트로만 남겼다. 다음에 그 코드를 고치는 사람은
같은 확인이 필요하다는 사실을 알 길이 없었다.

이 문서는 **무엇을 눈으로 봐야 하는지**와 **본 결과를 어떻게 남기는지**를 정한다.

## 1. 언제 수동 확인이 필요한가

넷 중 **하나라도** 해당하면 브라우저에서 직접 확인하고 결과를 남긴다.

| # | 기준 | 왜 |
|---|---|---|
| 1 | 정적 문자열 존재 검사만으로 **실제 호출 여부**를 보장할 수 없다 | 코드에 이름이 있는 것과 그것이 불리는 것은 다르다 |
| 2 | **실행 여부·호출 순서·중복 호출**이 결과를 바꾼다 | 순서가 뒤집혀도 두 호출 다 소스에는 그대로 있다 |
| 3 | **DOM 렌더링·포커스 이동·live-region·음성 안내**가 그 변경의 핵심이다 | 껍데기는 이것들을 모사하지 않는다 |
| 4 | `browser-shim` 정책상 브라우저 동작을 **의도적으로 안 흉내 내는** 자리다 | 검사를 늘려도 원리상 안 잡힌다 |

해당하지 않으면 이 절차를 밟지 않는다. **모든 프런트 PR 에 붙이는 요식이 아니다** —
그러면 아무도 안 읽는다.

## 2. 기록 형식

PR 본문에 아래 여섯 줄을 남긴다. 표 안에 다 들어가면 표로 써도 된다.

```text
대상          어느 동작의 무엇을 봤나
환경          브라우저 · 버전 · 화면 크기 (필요하면 보조기술)
조작          사용자가 실제로 한 것
기대 결과     무엇이 보이거나 들려야 하나
실제 결과     PASS / FAIL 과 관찰한 것
자동검사 한계 왜 이걸 검사로 못 잡는가
```

마지막 줄이 핵심이다. **왜 자동으로 못 잡는지 적지 못하면, 대개는 자동으로
잡을 수 있는 것이다** — 그때는 검사를 쓰는 편이 낫다.

## 3. 기록 예시 — KEY-129 / PR #131

이 절차를 만들게 한 사례다. 아래 내용은 2026-08-26 에 `develop` 에서 다시
확인했다.

```text
대상          문의하기 · PDF 저장 · 오류 신고를 눌렀을 때 `#guide-say` 갱신
환경          Chrome · 모바일 폭(375px) · VoiceOver
조작          세 버튼을 차례로 누른다
기대 결과     누를 때마다 안내 문구가 새로 읽히고, 빈 문자열로 덮이지 않는다
실제 결과     PASS — 셋 다 소리로 났다
자동검사 한계 아래 두 가지가 검사에 안 잡힌다
```

`notice()` 안의 `sayGuide(message)` 를 두 가지로 되돌려 봤다.

| 되돌린 내용 | `node --test frontend/tests/*.test.js` |
|---|---|
| `if (false) sayGuide(message);` — 호출을 막는다 | 종료코드 `0` · **안 잡힌다** |
| `sayGuide(message); sayGuide("");` — 곧바로 지운다 | 종료코드 `0` · **안 잡힌다** |

둘 다 소스에는 `sayGuide` 가 그대로 있어서 문자열 검사는 통과한다. 그런데 화면에
서는 아무 소리도 안 난다. **1번·2번·3번 기준에 동시에 해당하는 자리다.**

## 4. 어디에 남기나

- **PR 본문** — `.github/PULL_REQUEST_TEMPLATE.md` 의 「🖥 수동 브라우저 확인」 절.
  기본은 「해당 없음」이고, 1절에 걸리면 체크하고 2절 형식으로 적는다.
- 같은 화면을 여러 PR 이 반복해서 건드리면 이 문서 5절에 줄을 더한다.

## 5. 반복 확인이 필요한 자리

한 번 걸린 자리는 다음 사람도 지나간다. 여기 모아 둔다.

**병합 전** 표시가 붙은 줄은 아직 `develop` 에 없는 코드다. 해당 PR 이 병합되면
표시를 지운다 — 없는 자리를 가리킨 채 두면 다음 사람이 찾다 못 찾는다.

| 자리 | 무엇을 보나 | 왜 검사로 못 잡나 | 최초 근거 |
|---|---|---|---|
| `guide.js` `notice()` → `sayGuide()` | 세 버튼을 누를 때 안내가 소리로 나는가 | 호출 여부·후속 덮어쓰기를 껍데기가 모사하지 않는다 | KEY-129 / PR #131 |
| `guide.js` 챗봇 입력칸 포커스 복원 | 답변이 끝난 뒤 커서가 치던 자리에 남는가 | 포커스 이동은 껍데기에 없다 | KEY-130 / PR #135 — **병합 전** |

## 6. 이 절차가 바꾸지 않는 것

- 제품 코드와 기존 검사 동작은 건드리지 않는다.
- `browser-shim` 의 「그리지 않는다」 정책도 그대로 둔다. 이 문서는 그 정책의
  **대가를 어디에 적어 둘지**를 정할 뿐이다.
- 자동으로 잴 수 있는 것을 수동으로 미루는 근거로 쓰지 않는다. 2절 마지막 줄이
  그 방어선이다.
