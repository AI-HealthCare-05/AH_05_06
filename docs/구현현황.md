# 와이어프레임별 백엔드 API 구현 현황

> 출처: 2026-08-31 멘토링에서 정리한 스냅샷. Sprint 4 계획([`sprint4-plan.md`](sprint4-plan.md))의 기준선이다.
> 프레임 수는 정리 시점(와이어프레임 v2.3) 기준 62개이며, 정본 v2.3.1은 64개다([`wireframes/README.md`](wireframes/README.md)).

## 1. 문서 기준

이 문서는 와이어프레임 화면에 필요한 **백엔드 API 구현 여부**를 기준으로 정리한다.

> ✅로 표시된 항목도 프론트엔드 화면까지 완성됐다는 뜻은 아니다. API가 있어도 화면 연결과 사용자 테스트는 별도로 필요하다.
> 

### 범례

| 상태 | 의미 |
| --- | --- |
| ✅ 구현 | 화면에 필요한 핵심 백엔드 API가 구현됨 |
| ⚠ 부분 구현 | API 골격은 있으나 핵심 동작이나 데이터가 빠짐 |
| ❌ 미구현 | 필요한 API 또는 데이터 모델이 없음 |

## 3. MVP OTP 구현 방침

실제 SMS 공급자 연동 전까지 OTP 번호는 **임시 고정값 `000000`**으로 구현한다.

| 항목 | MVP | 후속 구현 |
| --- | --- | --- |
| OTP 요청 | 요청 성공 상태 반환 | 실제 SMS 발송 |
| OTP 번호 | 고정값 `000000` | 서버에서 난수 생성 |
| OTP 입력·검증 | `000000` 입력 시 통과 | 발급된 번호와 비교 |
| 실패 횟수·잠금 | 기존 로직 유지 | 기존 로직 유지 |
| 링크 만료·폐기 검사 | 유지 | 유지 |
| 인증 세션 | 정상 발급 | 정상 발급 |

따라서 `P1-1`의 실제 SMS 발송은 여전히 부분 구현이지만, **MVP 전체 흐름의 즉시 블로커에서는 제외**한다.

안전 조건:

- 고정 OTP는 로컬·개발·테스트 환경에서만 허용한다.
- 운영 환경에서는 `MOCK_OTP_CODE`가 설정돼도 인증 우회가 동작하지 않아야 한다.
- 링크 유효성, 만료, 폐기 및 5회 실패 잠금은 우회하지 않는다.
- 실제 환자 데이터가 아닌 합성 데이터로만 테스트한다.

예시:

```
MOCK_OTP_CODE=000000
```

## 9. 결론

백엔드 API 기준으로 전체 62개 프레임 중 절반인 31개가 구현돼 있다. 진료와 안내문 생성·승인, 환자 가이드, 챗봇 및 D+7 체크인의 기본 API는 준비된 상태다.

MVP에서는 실제 SMS 공급자 연동을 잠시 미루고 고정 OTP `000000`으로 인증 화면과 세션 흐름을 먼저 완성한다. 이후 발송 이력, 직원 관리, 병원별 설정을 구축하고 마지막에 실제 SMS OTP로 교체하는 순서가 적절하다.

> **MVP:** 스탭 검토 → 의사 승인 → 링크 발급 → 고정 OTP 인증 → 가이드 열람 → D+7 체크인
> 

> **운영 확장:** 실제 SMS 발송 → 발송·열람 이력 → 직원 관리 → 병원별 설정 → 감사로그
>
