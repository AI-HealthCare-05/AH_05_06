# D+7 확인 응답 API 계약 v1 (`KEY-138`)

> 화면: 와이어프레임 `P7-1` ~ `P7-6` · 선행: `KEY-98`([#55](https://github.com/AI-HealthCare-05/AH_05_06/pull/55))
> 이 문서가 정하는 것은 **「선택 즉시 알림」을 어떻게 보내는가** 하나다.

---

## 1. 무엇이 문제였나

와이어프레임이 세 화면(`P7-2` · `P7-4` · `P7-5`)에 같은 문장을 못박아 두었다.

> **선택 즉시 의료진 화면에 알림이 전송된다**

그런데 `#55` 로 들어간 구현은 `notify` 를 **저장할 때** 함께 보낸다. 그래서 이렇게 된다.

```
환자가 「불편해서 중단했어요」를 고른다   →  화면이 「병원에 문의해 주세요」를 띄운다
환자가 창을 닫는다                      →  의원은 아무것도 모른다
```

**끊은 환자가 곧 폼을 끝까지 채울 가능성이 가장 낮은 환자다.** 지금 계약은 그 사람을 놓친다.

---

## 2. 결정 — 신호와 답을 갈라 둔다

**「선택할 때마다 별도 호출」(안 1)을 고른다.**

| | 무엇 | 언제 |
|---|---|---|
| **신호** `POST /checkins/{token}/signals` | 「지금 이걸 골랐다」 | 선택 즉시 |
| **답** `POST /checkins/{token}` | 통증·유형·메모까지 담은 최종 제출 | 저장 버튼 |

### 왜 「저장 API 자동 호출」(안 2)이 아닌가

* **「저장」 버튼의 뜻이 사라진다.** 환자는 아직 제출하지 않았다고 믿는데 통증 점수·메모가 반쯤 저장된다. 화면에 버튼이 있는데 누르기 전에 이미 저장돼 있으면, 그 버튼은 거짓말이다
* **와이어프레임도 둘을 구분한다.** 「알림이 전송된다」이지 「답이 저장된다」가 아니다
* 답을 바꿀 때마다 부분 제출이 쌓인다

### 중복·철회·정정 — 한 규칙으로 끝낸다

> **신호는 토큰 하나에 하나다. 다시 고르면 덮어쓴다.**

이력이 아니라 **「지금 고른 것」** 이다. 그래서

* 「중단」 → 「잘 먹고 있어요」로 바꾸면 신호도 바뀐다. 의원은 최종 답만 본다
* 같은 답을 여러 번 눌러도 알림이 늘지 않는다
* 저장이 오면 **저장이 최종**이다. 신호는 저장 전의 임시 상태다

환자가 망설인 사실은 남기지 않는다. 남기면 의원이 없는 문제를 쫓게 되고, 그러면 다음부터 그 표시를 안 믿는다.

### 그래서 화면은 **고른 것을 늘 보낸다**

알림 대상인 답만 보내면 **철회가 안 된다.** 브라우저에서 눌러 확인한 것이다.

```
「불편해서 중단했어요」 고름   →  신호 감  →  의원 화면에 알림
「잘 먹고 있어요」로 바꿈      →  안 보냄  →  중단 신호가 그대로 남는다
저장하지 않고 창을 닫음        →  의원은 없는 문제를 쫓는다
```

`taking` · `missing` 도 보낸다. **서버가 알림을 만들지 않을 뿐**이고, 신호는 덮어써져 앞의 알림이 거둬진다.

「가끔 놓쳐요」를 보내도 환자에게 연락이 가지 않는다 — `P7-3` 이 지키려던 것은 「연락하지 않는다」이지 「서버가 모른다」가 아니다. 그 화면의 노트도 **「의료진에게는 기록만 남는다」** 라고 적어 두었다.

## 3. 요청·응답

### `POST /checkins/{token}/signals`

```json
{ "medication": "stopped_side_effect" }
```

| | |
|---|---|
| `200` | `{ "signaled": true }` — 알림을 만들었다 |
| `200` | `{ "signaled": false }` — 알림 대상이 아닌 답이다 (아래 §4) |
| `410` | `LINK_EXPIRED` — 링크가 닫혔다 |
| `422` | `MEDICATION_REQUIRED` — 정의 밖의 값 |

**응답을 화면이 기다리지 않는다.** 신호가 실패해도 환자는 계속 답할 수 있어야 한다 — 알림은 의원 쪽 편의이고, 환자의 제출을 막을 이유가 없다.

### 답 저장은 그대로다

`POST /checkins/{token}` 의 모양은 `#55` 에서 바뀌지 않는다. `notify` 필드도 그대로 보낸다 — 화면이 「원장님께 전해드릴게요」라고 말해 놓고 서버는 모르는 상태를 막는 대조용이다.

## 4. 어느 답이 알림을 만드는가 — **서버가 정한다**

```
taking               잘 먹고 있어요            알림 없음
uncomfortable        먹고 있는데 불편해요       알림
missing              가끔 놓쳐요               알림 없음 · 기록만
stopped_side_effect  불편해서 중단했어요        알림
stopped_improved     좋아져서 그만뒀어요        알림
```

이 표는 `GET /checkins/{token}` 이 선택지마다 내려주는 `notify` 가 정본이다. **화면은 판단하지 않는다** — 무엇이 알릴 일인지는 승인된 주의사항이 정한다.

화면이 `POST` 에 실어 보내는 `notify` 는 **대조용이지 근거가 아니다.** 서버는 자기 표로 판단하고, 값이 다르면 그것만으로 기록을 남길 수 있다.

### 「가끔 놓쳐요」에 알림을 달지 않는 이유

`P7-3` 노트가 적어 두었다.

> 책망하지 않는다. 「가끔 놓쳐요」는 솔직하게 답한 것이고, 그 자리에서 「잘 챙기셔야 합니다」가 나오면 다음 회차부터는 「잘 먹고 있어요」를 고른다. **그러면 우리가 보는 숫자가 거짓이 된다.**

알림을 만들면 의원이 연락하게 되고, 연락하면 환자는 다음부터 솔직하게 답하지 않는다.

> ⚠️ **와이어프레임 `P7-3` 안에서 세 줄이 서로 다르게 말한다.** 헤더는 「🔔 알림을 만들지 않는다」, 노트는 「의료진에게는 기록만 남는다」인데, 카드 아래 공통 캡션만 「선택 즉시 알림이 전송된다」로 남아 있었다. 캡션이 `P7-2`·`P7-4` 에서 복사되며 딸려온 것으로 보여 **`P7-3` 의 캡션을 고쳤다.** 다르게 보시면 알려 주세요 — 그 경우 이 절과 목업의 `missing.notify` 를 함께 바꿔야 한다.
