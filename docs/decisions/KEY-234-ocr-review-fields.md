## 1. 항목 전체 (14종)

`OcrField.field_type` 이 실제로 갖는 값이다. **화면의 한글 이름표는
`frontend/js/field-labels.js` 가 갖는다** — 서버는 코드만 준다.

### ① 진단 · 처방 — 안내문의 뼈대

| # | 코드 | 화면 이름 | 단위 | 어디서 읽나 | 없으면 |
|---|---|---|---|---|---|
| 1 | `DIAGNOSIS` | 진단 | — | EMR 상병 | 어느 주의 문구를 붙일지 못 정한다 |
| 2 | `MEDICATION_NAME` | 약품명 | — | EMR 처방표 `약품명` 열 | 안내문에 약 이름이 안 들어간다 |
| 3 | `DOSAGE` | 1회량 | — | 처방표 `1회량` 열 | 복용법을 못 쓴다 |
| 4 | `FREQUENCY` | 일일횟수 | — | 처방표 `일일횟수` 열 | 복용법을 못 쓴다 |
| 5 | `DURATION_DAYS` | 처방일수 | 일 | 처방표 `처방일수` 열 | **소진 임박 안내를 못 보낸다** |
| 6 | `PRESCRIPTION_DATE` | 처방일 | — | 처방표 | 소진 예정일을 못 센다 |

**소진 예정일은 항목이 아니다.** `처방일 + 처방일수` 로 화면이 계산한다
(`frontend/js/ocr-groups.js` `runOutDate`). 판독한 값처럼 보이면 스탭이
원문에서 찾으려 들기 때문에 화면에 「(계산)」이라 붙인다.

`DURATION_DAYS` 가 28 미만이면 확인 줄을 띄운다. EMR 「총투」 칸에 일수 대신
**총 알 수**가 찍혀 오는 일이 있어서다. 막지는 않는다 — 짧은 처방도 있다.

### ② 이번 판독 값 — 검사

| # | 코드 | 화면 이름 | 단위 |
|---|---|---|---|
| 7 | `LAB_DATE` | 검사일 | — |
| 8 | `HEMOGLOBIN` | 혈색소 | g/dL |
| 9 | `ENDOMETRIOMA_SIZE` | 자궁내막종 | cm |
| 10 | `ENDOMETRIAL_THICKNESS` | 내막 두께 | cm |
| 11 | `AMH` | AMH | ng/mL |
| 12 | `E2` | E2 (에스트라디올) | pg/mL |
| 13 | `AST_ALT` | 간수치 AST/ALT | U/L |
| 14 | `CRP` | CRP | mg/L |
| 15 | `CA_125` | CA-125 | U/mL |
| 16 | `CA19_9` | CA 19-9 | U/mL |

`LAB_DATE` 는 **값 줄이 아니라 묶음 머리**에 붙는다 (「이번 판독 값 · 검사일
08-05」). 줄로도 세우면 같은 것이 두 번 보인다.

> 세어 보면 16 이지만 항목은 14 종이다 — `LAB_DATE` 는 머리줄이고,
> `DIAGNOSIS` 는 ①의 머리줄에도 쓰인다.

### ③ 이전 값 유지 · ④ 확인 항목 — **아직 서버에 자리가 없다**

와이어프레임이 그렸지만 채울 데이터가 없다.

**막힌 곳이 서로 다르다.** 뭉뚱그려 「서버에 자리가 없다」고 하면 둘 다 표부터
만들어야 하는 줄 알게 된다.

| 묶음 | 표 | 길(API) | 막힌 곳 |
|---|---|---|---|
| ③ 이전 값 유지 | **있다** — 지난 진료의 확정 값이 `ocr_field` 에 그대로 쌓여 있다 | 없다 | **길** |
| ④ 확인 항목 | **없다** — 처방별 항목 목록도, 스탭이 체크한 답을 진료에 붙일 자리도 없다 | 없다 | **표부터** |

③ 은 표를 새로 만들 필요가 없다. 판독 API 가 전부 `ocr_job_id` 나 이번 진료로만
열려 있어서(`app/ocr/api.py` 의 6개 경로), 지난 진료의 확정 값을 꺼내는 경로
하나가 없을 뿐이다.

④ 는 `prescription_set`(8종)과 `drug_caution_content`(문구)가 있지만, 처방별로
무엇을 여쭐지의 **목록**도, 스탭이 체크한 **답**을 붙여 둘 자리도 없다.
`visit.doctor_note` 는 의사 소견 칸이라 이것과 다르다.

화면은 ④의 체크박스를 **꺼진 채로** 세운다. 켤 수 있게 두면 스탭이 「우울증
병력」을 체크하고 저장됐다고 믿는데 아무 데도 안 남는다 — 안전에 걸리는 항목이라
그 오해가 가장 나쁘다.

화면은 이 둘을 **점선 테두리에 「서버에 아직 자리가 없습니다」** 로 세운다.
목업 값을 채워 두면 되는 것처럼 보이고, 그게 1차 시연이 멈춘 방식이다.

## 2. 항목마다 화면이 갖는 상태

`OcrFieldResponse` (`app/ocr/schemas.py`) 가 주는 것으로 가른다.

| 상태 | 조건 | 화면 |
|---|---|---|
| 읽음 | `value` 있음 · 신뢰도 정상 | 값 + 단위 + 출처 배지 |
| 확인 필요 | `is_low_confidence` | 값 + 「확인 필요」 |
| 값 2개 | `candidates` 2개 이상 | 후보를 나란히 · 고르기 |
| **못 읽음** | `value` 없음 | **점선 + `?`** · 단위 빈칸 · 「⚠ 인식 실패」 · [ 직접 입력 ] |
| 추후 보고 | `is_pending_report` | 「추후 보고 예정 · 별도 보고 검사」 (AMH 가 그렇다) |
| 확정됨 | `is_confirmed` | 잠긴 값 — 더 볼 것이 없다 |

**못 읽은 값은 「확인 완료 · 안내문 생성」을 막지 않는다.** 와이어프레임
S1-7 이 바로 그 상태를 그린 프레임이고, 거기서 그 버튼은 살아 있는 색이며
흐름 줄이 「못 읽은 값 없이 생성」이라 적는다. 막는 것은 **충돌** 하나다 —
같은 항목이 두 곳에 다른 값으로 있으면 사람이 골라야 한다.

## 3. 확인해야 할 두 가지 — 팀에 알림

### ⓐ 확정한 값이 안내문에 거의 안 쓰인다

`app/services/guides.py:82`

```python
confirmed = await OcrField.filter(..., is_confirmed=True).first()
field_label = f"{confirmed.field_type}: {confirmed.value}"
```

`.first()` 다 — **확정 항목 중 아무거나 하나**만 쓴다. 스탭이 14개를 확인해도
안내문에 실리는 것은 한 개고, 그것도 `MEDICATION_NAME: 비잔` 처럼 **영문
코드째로** 환자 글에 들어간다.

### ⓑ 확정한 값이 `Prescription` 으로 넘어가지 않는다

안내문의 주의 문구는 처방 세트로 고른다.

```python
prescription = await Prescription.filter(visit_id=visit_id).first()
set_name = prescription.prescription_set if prescription else None
```

그런데 운영 코드에 `Prescription.create` · `PrescriptionItem.create` 가
**없다** (테스트에만 있다). 그래서 `set_name` 은 항상 `None` 이고, 주의 문구는
늘 폴백으로 간다 — 처방과 무관한 일반 문구가 나간다.

`PrescriptionItem` 은 `name` · `frequency` · `duration_days` 를 갖고 있어
판독 항목 ②③⑤와 그대로 짝이 맞는다. **다리만 없다.**

> 이 두 가지는 화면이 아니라 서버 몫이다. 판독 API 구현을 맡는 분께
> 넘긴다 — 화면은 위 목록대로 값을 확정해서 보낸다.

## 4. 화면이 지키는 규칙

- 항목 이름은 **한글로만** 보인다 (`fieldLabel`). 모르는 코드는 코드 그대로
  보여 준다 — 빈칸으로 두면 값이 있는데 없는 것처럼 보인다.
- 이름표는 **한 곳**에 있다. 판독 화면 · 안내문 · 의사 화면이 같은 항목을
  다르게 부르면 같은 값인지 알 수 없다.
- 추출기에 코드가 하나 늘면 `tests/field-labels.test.js` 가 먼저 깨진다 —
  `field_extractor.py` 원문을 읽어다 대조한다.
