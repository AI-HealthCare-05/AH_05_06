# KEY-163 실제 OCR 1종 문서·핵심 필드·fallback 기준 결정 기록

상태: **2026-08-25 초안 — 8/27 멘토링 후 확정 예정**

## 목적

Walking Skeleton(8/27)에서 사용 중인 fixture OCR을 실제 CLOVA OCR 1종으로 교체할 때 필요한 최소 계약을 고정한다.
무엇을 구현할지가 아니라 구현 전에 팀이 동의해야 할 경계와 판정 기준을 확정하는 것이 이 문서의 역할이다.

- 부모: KEY-142
- 구현 일감: KEY-56 (CLOVA OCR 어댑터)
- 연계: KEY-69 (E2E 검증), KEY-70 (보안 회귀), KEY-61·KEY-133 (완료)

## 1. 지원 문서 유형 1종

### 초안 방향: EMR 유력

와이어프레임 S1-5에서 EMR 과거기록이 "안내문 생성 필수 ★"이며 "이 화면만으로 충분합니다"로 명시된다.
EMR 1장에 진단(상병) · 처방 · 검사 수치가 모두 포함되어, 처방전·검사지보다 단일 문서 커버리지가 넓다.

MVP 구현은 특정 병원 1곳의 EMR 캡처 화면을 기준으로 하는 방향을 검토 중이다. 해당 병원 EMR 화면을 직접 확인한 결과, 진단과 처방 정보가 각각 별도의 표로 구조화되어 있음을 확인했다. 셀 단위로 추출 가능한 레이아웃이라 자연어 파싱보다 안정적일 것으로 예상된다.

| 유형 | 판단 |
|------|------|
| **EMR** | **유력** — 와이어프레임 의도와 일치. 단일 병원 고정으로 레이아웃 일관성 확보 예상. 처방 정보가 표 형태라 셀 추출 가능할 것으로 보임 |
| PRESCRIPTION | 처방 정보만 포함. 진단·검사 수치가 빠져 안내 품질 저하 우려 |
| LAB_RESULT | EMR에 없는 추가 검사 항목 보완용 |

**MVP 한정 범위 안내** — 공식 데이터 흐름도(화면 흐름도 v2.0.0 §5)에는 `EMR · 처방전 · 검사지` 3종이 모두 OCR 입력으로 명시된다. 이번 KEY-163은 9/3 MVP 기한 내 실동작 검증을 위해 EMR 1종으로 범위를 한정하는 결정이며, 처방전·검사지 지원은 이후 단계(KEY-142 이후)에서 확장할 예정이다.

> 8/27 멘토링 확정 항목: EMR 최종 선택 여부, 대상 병원 EMR 시스템 이름·버전 기록

## 2. 핵심 필드 최소 집합

### EMR 기준 (초안)

아래 필드는 `OcrField.field_type` 값으로 사용할 후보다.
`OcrField`는 `(ocr_result, field_type)` unique 제약이 있어 유형당 한 필드만 저장된다.

확인된 EMR 화면 레이아웃을 바탕으로 아래 위치에서 추출을 시도한다.

```
[메모] 자유 텍스트 — 추출 범위 밖
[진단 표] ICD코드 | 상병명 | 진료과 | 투약구분 | 주/부상병 구분
[처방 표] 코드 | 약품명 | 1회량 | 일일횟수 | 처방일수 | 수량 | 금액
```

주상병(주상병 체크 컬럼 기준)을 `DIAGNOSIS`의 우선 추출 대상으로 삼는다.
부상병이 여러 개일 경우 이번 범위에서는 주상병 1개만 추출한다.

**추출값의 역할 — 처방 세트 대조** (화면 흐름도 v2.0.0 §5)

OCR 추출값은 안내문 텍스트에 직접 삽입되지 않는다. 아래 흐름으로 사용된다.

```
DIAGNOSIS + MEDICATION_NAME
    → 처방 세트 8종 중 매칭 (예: 비잔 → "비잔 기본 처방")
    → 매칭된 세트의 안내 부품 조립
    → 안내문 생성
```

`DURATION_DAYS`는 세트 매칭이 아닌 소진예정일 계산(`기준일 + 처방일수`)에만 쓰인다.
`DOSAGE`·`FREQUENCY`는 세트 내 안내 문구가 이미 용법을 포함하므로 권장으로 분류한다.

**검사 수치·검사일이 이번 범위 밖인 이유**

공식 흐름도에는 `수치(혈색소·CA-125 등)`와 `검사일`도 추출 대상으로 명시된다.
이번 MVP에서 이를 범위 밖으로 두는 이유는 중요하지 않아서가 아니라, 수치를 OCR로 못 읽더라도 판독 확인 화면(S1-d/e)에서 스탭이 직접 입력할 수 있어 E2E 흐름이 끊기지 않기 때문이다. 수치·검사일 자동 추출은 이후 고도화 단계에서 추가한다.

| field_type | 설명 | 필수 여부 | EMR 내 위치 |
|---|---|---|---|
| `DIAGNOSIS` | 진단명 및 ICD 코드 | **필수** | 진단 표 — 주상병 행의 상병명·ICD코드 컬럼 |
| `MEDICATION_NAME` | 약품명 | **필수** | 처방 표 — 약품명 컬럼. 복약 안내 생성의 핵심 입력 |
| `DURATION_DAYS` | 처방 일수 | **필수** | 처방 표 — 처방일수 컬럼. 소진예정일 계산 근거. `28` 미만이면 사람 확인 권고 (`docs/synthetic-data-spec.md` SYN-PCOS-02) |
| `DOSAGE` | 1회 투여량 | 권장 | 처방 표 — 1회량 컬럼. 없으면 안내 품질 저하 |
| `FREQUENCY` | 일일 복용 횟수 | 권장 | 처방 표 — 일일횟수 컬럼. 없으면 안내 품질 저하 |

필수 필드 후보(`DIAGNOSIS`, `MEDICATION_NAME`, `DURATION_DAYS`) 중 하나라도 누락되면 실제 OCR 성공으로 보지 않고 fallback으로 진입하는 방향을 제안한다.

**출처 기록 요건** (화면 흐름도 v2.0.0 §5 "출처 기록 — 어느 장에서 읽었나")

CLOVA OCR 어댑터(KEY-56)는 각 필드를 저장할 때 아래 모델 필드도 함께 채워야 한다.
이 값은 와이어프레임 S1-8(같은 항목이 두 곳에 있을 때 출처 비교)과 승인 후 원본 삭제 추적에 사용된다.

| 모델 필드 | 채울 내용 |
|---|---|
| `OcrDocumentText.document_id` | 추출에 사용한 문서의 `document_id` |
| `OcrField.document_text_id` | 해당 필드가 속한 `OcrDocumentText` |
| `OcrField.source_line` | 가능하면 EMR 내 행 번호 또는 셀 좌표 |

> 8/27 멘토링 확정 항목: 필수·권장 분류 최종 승인, 해당 병원 EMR 처방 표 컬럼명 확인

## 3. 합성 문서 샘플과 테스트 입력 기준

### 원칙

- 실제 환자 정보를 사용하지 않는다. `docs/synthetic-data-spec.md` 1절 절대 규칙을 따른다.
- 팀 공용 시나리오 ID(`SYN-EMS-01`, `SYN-PCOS-01`)를 기반으로 만든다.
- 실제 환자가 포함된 EMR 화면 캡처를 저장소에 커밋하지 않는다.

### 합성 EMR 샘플 기준 (초안)

EMR 문서 유형 확정 시, 확인된 병원 EMR 화면 레이아웃을 그대로 따르되 모든 값은 합성 데이터로 채운다.
실제 환자가 포함된 EMR 화면 캡처는 OCR 개발·테스트 목적으로도 저장소에 커밋하지 않는다.

**진단 표 합성값**

| 컬럼 | 합성값 | 근거 |
|---|---|---|
| ICD코드 | N809 | SYN-EMS-01 (자궁내막증) |
| 상병명 | 상세불명의 자궁내막증 | SYN-EMS-01 |
| 주/부상병 | 주상병 | — |

**처방 표 합성값**

| 컬럼 | 합성값 | 근거 |
|---|---|---|
| 약품명 | 비잔정(디에노게스트) 2mg | SYN-EMS-01 처방 세트 |
| 1회량 | 1 | — |
| 일일횟수 | 1 | — |
| 처방일수 | 84 | SYN-EMS-01 (3통수 × 28일) |

**기타 합성값**

| 항목 | 합성값 | 근거 |
|---|---|---|
| 환자명 | 김서연 | SYN-DUP-03 |
| 담당의 | 박연 | SYN-STAFF-02 |
| 처방일 | 2026-08-01 (예시) | 합성값 |

합성 EMR 이미지는 대상 병원 화면 레이아웃을 재현해 만든다.
CLOVA OCR 테스트용 이미지는 저장소가 아닌 별도 경로에 보관하며 실제 환자 정보를 포함하지 않는다.

> 8/27 멘토링 확정 항목: CLOVA OCR 개발 계정 접근 가능 여부, 합성 EMR 이미지 보관 위치

## 4. 성공 판정과 fallback 진입 조건

### 판정 분류

| 상황 | 판정 | 동작 |
|------|------|------|
| CLOVA OCR 호출 성공 + 필수 필드 전부 추출 | **실제 OCR 성공** | `OcrResult.model_name = "clova-ocr-v1"` 저장, 정상 수정·확정 흐름 진행 |
| 필수 필드 중 하나라도 누락 | **필드 누락** | fallback 진입. `OcrJob.failure_code = "REQUIRED_FIELD_MISSING"` |
| CLOVA OCR API 오류 (5xx, timeout) | **외부 오류** | fallback 진입. `OcrJob.failure_code = "CLOVA_API_ERROR"` |
| fallback 진입 후 fixture 결과 생성 | **fixture fallback** | `OcrResult.model_name = "fixture-v0"` 저장. 기존 수정·확정 흐름 유지 |

### fallback 불변 조건

- fallback 진입 시에도 `OcrJob` → `OcrResult` → `OcrField` 구조는 동일하게 생성된다.
- fixture fallback은 기존 수정·확정·안내 흐름을 우회하지 않는다.
- `model_name` 필드로 실제 OCR 모드와 fallback 모드를 구분할 수 있어야 한다.
- 타 병원 식별자는 fallback 여부와 무관하게 `404`로 처리된다.

> 8/27 멘토링 확정 항목: timeout 기준값 (초안: 10초), fallback 허용 범위

## 5. 증적 로그 형식

처리 결과는 기존 모델 필드로 기록한다. 새 컬럼을 추가하지 않는다.

| 기록 위치 | 필드 | 기록 내용 |
|---|---|---|
| `OcrJob` | `started_at` | CLOVA OCR 호출 시작 시각 |
| `OcrJob` | `completed_at` | 결과 저장 완료 시각 |
| `OcrJob` | `failure_code` | 실패 원인 코드 (`CLOVA_API_ERROR`, `REQUIRED_FIELD_MISSING`) |
| `OcrResult` | `model_name` | `"clova-ocr-v1"` 또는 `"fixture-v0"` |

**처리시간**은 `completed_at − started_at`으로 파생하며 별도 컬럼을 추가하지 않는다.

PR에 기록할 실행 증적:
- 실제 OCR 모드: 성공 여부, `model_name`, 처리시간, 추출된 필드 목록 (값 본문 제외)
- fallback 모드: `failure_code`, fallback 후 E2E 흐름 완주 여부
- 실제 환자 정보·API 키·EMR 원문을 PR·로그·커밋에 남기지 않는다.

## 7. 구현 후 회귀 시나리오

- 실제 OCR 성공 시 `model_name = "clova-ocr-v1"`, 처리시간이 기록됨
- 실제 OCR 실패 시 `failure_code`가 설정되고 fixture fallback으로 전환됨
- fallback 이후 수정·확정·안내 생성·환자 조회·D+7 흐름이 중단 없이 완주됨
- `model_name = "fixture-v0"` 상태에서도 기존 회귀 테스트가 통과함
- CLOVA API 키·EMR 원문이 응답·로그·커밋에 노출되지 않음
- 타 병원 진료의 OCR 작업 접근이 `404`로 차단됨
