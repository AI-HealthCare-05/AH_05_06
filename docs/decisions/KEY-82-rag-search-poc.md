# KEY-82 승인 의료지식 검색 경계와 MySQL 8 PoC 결정

상태: **구현·리뷰 전 초안**  
상위: KEY-75 · 관련: KEY-5, KEY-96, KEY-165, KEY-180  
담당: 유가은 · 리뷰어: 한금준, 권일준, 이희진

## 1. 결론

- **PoC 평가 통과 전에는 안내 생성과 연결하지 않는다.** 현재 합성 7건 PoC는 저장·검색 경계의
  재현만 확인한 상태이며 생성 연결 승인으로 간주하지 않는다.
- 평가 통과 후에도 이 계약의 모든 필터와 충돌 검사를 통과한 검색 결과만 생성 컨텍스트에 넣는다.
- 결과가 없으면 사전에 의료 안전 검수자가 승인한 현재 버전의 고정 템플릿으로만 fallback한다.
  검색 충돌·인덱스 오류는 `근거 없음`으로 바꾸지 않고 생성 자체를 차단한다.
- 생성 컨텍스트 진입에는 합격 결과의 checksum이 연결된 지정 리뷰어 승인 기록이 필요하다.
  단순 boolean이나 검색 성공만으로 생성 연결을 열 수 없다.
- 로컬·Pilot DB는 **MySQL 8.0을 유지**한다.
- 원문은 비공개 MinIO에 두고, 추출 텍스트·청크·출처·버전·승인 상태·임베딩은 MySQL 8에 둔다.
- 초기 규모에서는 MySQL이 승인 후보를 필터링하고 Python 애플리케이션이 코사인 유사도를 계산한다.
- 검색 결과는 안내문 **초안의 근거 후보**다. 환자에게 직접 노출하거나 자동 승인하지 않는다.
- KEY-96 챗봇은 지금처럼 해당 환자의 승인 완료 `GuideSection.body`만 사용한다. 이 RAG 검색으로 바꾸지 않는다.

MySQL 9의 `VECTOR` 저장 기능만을 이유로 메이저 업그레이드하지 않는다. 저장 타입과 유사도
검색 함수·인덱스, ORM·마이그레이션 지원은 서로 다른 문제다. 현재 규모에서 JSON 벡터를
후보 행과 함께 읽어 Python으로 계산하는 경로가 재현되므로 DB 변경 위험을 먼저 만들지 않는다.

## 2. 검색·답변 범위

### 검색하는 것

- 안내 섹션 `medication`, `caution`, `emergency`, `life`를 뒷받침하는 승인 의료지식
- 식약처·공공기관 자료와 병원 의료진이 검수·승인한 내부 교육 문서
- `APPROVED`이면서 현재 버전이고, 이용조건과 설정된 검토 기한이 유효한 청크

### 검색하지 않는 것

- 환자·진료·OCR 원문, 처방전 이미지, 환자 질문·챗봇 대화
- `DRAFT`, `DEPRECATED`, 과거 버전, 검토 기한 만료, 이용조건 미확인 자료
- 다른 병원 전용 자료
- 병원 행정 문구인 `messages`와 범위 밖 질문

검색은 진단, 처방 선택, 약의 중단·변경·증량·감량을 결정하지 않는다. 근거가 있어도 기존
안내 생성 → 의료진 검토 → 승인 흐름을 건너뛸 수 없다. 응급 표현은 승인된 원문을 완화하지 않는다.

### 수집·추출 경계

- 텍스트 PDF와 공공 API 응답은 원문 checksum과 추출기 버전을 함께 기록한다.
- 스캔 PDF·이미지는 OCR 결과를 자동 승인하지 않고 원본 페이지 좌표와 함께 `DRAFT`로 적재한다.
- 표·경고·금기 문구의 구조가 보존되지 않거나 OCR 신뢰도가 기준 미달이면 색인하지 않는다.
- 외부 임베딩·생성 모델에는 환자·진료·OCR 원문과 병원 전용 식별자를 보내지 않는다.
  Pilot은 로컬 임베딩만 사용하며 외부 전송 추가는 별도 보안·의료 검토 대상으로 둔다.

## 3. 출처와 승인 계약

KEY-180의 등급을 재사용한다. A등급만 단독 검색 근거로 사용한다. B등급은 사람이 문구를
검토할 때만 참고할 수 있고 검색 결과에는 들어오지 않는다. C등급과 이용조건 미확인 자료는 사용하지 않는다.

한 문서 버전에는 자료명, 발행기관, 원문 위치, 확인일, 기준일·버전, 등급, 이용조건 확인,
검수자, 승인 시각, 다음 검토일을 기록한다. 새 버전 승인과 이전 버전 `DEPRECATED` 전환은
한 트랜잭션에서 수행하며 `(문서, 현재 승인 버전)`은 DB 유니크 제약으로 하나만 허용한다.

## 4. 저장 구조 계약

후속 지식 파이프라인이 구현할 논리 구조다. KEY-82 PoC는 운영 테이블을 만들지 않고 같은 칼럼의
MySQL `TEMPORARY TABLE`을 사용한다.

| 구조 | 핵심 칼럼 |
|---|---|
| `knowledge_document` | 문서 UUID, 공유/병원 범위, 자료명·기관·원문 URL, MinIO object key, 이용조건 |
| `knowledge_version` | 버전 UUID, 문서 UUID, checksum, 기준일·확인일·다음 검토일, 등급, 승인 상태, 검수자 |
| `knowledge_chunk` | 청크 UUID, 버전 UUID, 섹션, 순서, 본문, claim key/value, 임베딩 JSON, 모델·차원 |

- 공공 공통 자료의 `hospital_id`는 `NULL`, 병원 자체 자료는 해당 `hospital_id`를 갖는다.
- 후보 SQL은 `APPROVED + current + A + 이용조건 확인 + 설정된 검토기한 + 병원 + 섹션`을 먼저 거른다.
- 애플리케이션은 같은 조건을 다시 확인한다. 타 병원 행은 점수 계산 전 제외한다.
- 임베딩 모델은
  [`sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`](https://huggingface.co/sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2),
  차원은 **384**, 최초 리비전은 `e8f8c211226b894fcb81acc59f3b34ba3efd5f42`로 고정한다.
  사용한 리비전을 저장하고 변경 시 전량 재색인한다.
- 청킹은 제목 경계를 보존한 문단 단위, 최대 800자, 문장 경계 기준 120자 이내 겹침으로 시작한다.
  표의 한 행과 경고 문장은 쪼개지 않는다.

## 5. 검색 계약

- 거리: cosine similarity
- `top-k`: **3**
- 최소 유사도: **0.72**
- 동점: `chunk_id` 오름차순으로 결정해 재현성을 유지한다.
- PoC 원본 벡터는 알고리즘·경계 재현이 쉬운 3차원 합성값이며, 평가·검색 직전에 나머지를 0으로
  채워 384차원 계약을 동일하게 강제한다. 운영 384차원 품질 임계값은 승인 질의셋으로 다시
  측정하되, 별도 결정 없이 0.72를 낮추지 않는다.
- 출처 충돌은 반환될 `top-k`에 한정하지 않고 최소 유사도 이상인 전체 후보에서 검사한다. 하위
  후보에 상충 근거가 있어도 안전상 전체 검색을 차단한다.

### 실패 폐쇄(fail closed)

| 상황 | 결과 |
|---|---|
| 임계값 이상 근거 없음 | `NO_EVIDENCE`; 사전 승인된 현재 버전의 고정 템플릿만 사용 |
| 미승인·폐기·만료·이용조건 미확인 | 후보에서 제외 |
| 같은 claim의 상충된 값이 동시에 검색됨 | `SOURCE_CONFLICT`; 결과 전체 차단 |
| 타 병원 자료 | 점수 계산 전에 제외하고 원문·존재 여부를 응답에 노출하지 않음 |
| 임베딩 차원 불일치·0 벡터 | `INDEX_INVALID`; 부분 검색하지 않고 재색인 요청 |
| DB·MinIO·임베딩 모델 실패 | `GENERATION_BLOCKED`; 검색 컨텍스트와 fallback 모두 금지 |

위 표의 `NO_EVIDENCE` fallback은 모델이 새 문장을 생성하는 것이 아니라,
`approval_status=APPROVED`, 현재 버전, 빈 본문 아님을 모두 검증한 고정 템플릿을 그대로 반환하는
것만 뜻한다. 검색 충돌, 임베딩 불일치, 저장소 오류에는 fallback 템플릿을 사용하지 않는다.
이 구분은 `admit_generation_context()`가 강제한다.

로그에는 청크·문서 식별자, 모델 리비전, 점수, 결과 코드, 지연시간만 남긴다. 환자정보, 질문·답변
원문, 링크 토큰, OCR 원문은 남기지 않는다.

## 6. PoC 재현

```bash
docker compose exec -T fastapi \
  uv run --no-sync python scripts/key82_rag_poc.py --iterations 50

uv run --group app pytest -q --confcutdir=app/tests/rag app/tests/rag

uv run --no-sync python scripts/key82_rag_evaluate.py
```

PoC는 `docs/data/key82-rag-poc-chunks.json`의 합성 데이터만 임시 테이블에 넣는다. 기존 테이블과
볼륨을 만들거나 지우지 않는다. 출력에는 결과 코드·청크 ID·점수·p50/p95만 포함한다.
결과가 `FOUND`가 아니거나 기대 청크가 정확히 선택되지 않으면 종료코드 1을 반환하므로 CI와
배포 점검에서 PoC 실패를 자동 판정할 수 있다.

2026-09-07 로컬 Docker MySQL 8.0.46에서 9개 합성 행, 50회 반복 결과는 `FOUND`, 현재 승인 청크
1건만 선택, p50 0.352ms·p95 0.567ms였다. 작은 기능 재현 결과이며 운영 용량 성능을 뜻하지 않는다.

### 합성 retrieval 평가 기준과 결과

평가셋은 정상·유사·무관·검색 대상이 없는 섹션·미승인/폐기/타 병원 제외·승인 출처 충돌을
포함한 6개 질의로 고정했다. 안전 지표는 단 한 건의 위반도 허용하지 않는다.
positive case가 하나도 없어 Recall/Precision 분모가 0이면 해당 지표를 `null`로 기록하고
평가 전체를 불합격 처리한다. negative case만으로 품질 평가가 통과하거나 실행이 중단되지 않는다.

| 지표 | 합격 기준 | 2026-09-07 결과 |
|---|---:|---:|
| 결과 코드 정확도 | 100% | 100% |
| Recall@3 | 90% 이상 | 100% |
| Precision@3 | 90% 이상 | 100% |
| 컨텍스트/fallback/차단 경로 정확도 | 100% | 100% |
| 금지 근거의 컨텍스트 진입 | 0건 | 0건 |

평가 결과 checksum은
`0a6c9161d77a65dbf860c3d4d7eaf9c0efe5ee768bced68db514f5716da87bb5`다.
평가 스크립트의 `passed=true`는 합성 기술 평가를 통과했다는 뜻이다. 생성 연결 승인은 별개이며,
지정 리뷰어가 평가 결과 checksum을 확인하고 승인 기록을 남기기 전에는 진입문을 열지 않는다.

### 생성 연결 평가 문턱

다음 조건이 모두 충족되고 지정 리뷰어가 결과를 승인하기 전에는 `GuideService`, `ChatbotService`,
환자 화면에 이 검색을 연결하지 않는다.

1. 승인 질의·정답·금지 근거가 포함된 별도 합성 평가셋을 의료 안전 검수자가 승인한다.
2. 미승인·폐기·만료·타 병원·상충 근거가 컨텍스트에 들어간 사례가 0건이다.
3. 근거 없는 질의가 승인 템플릿 외 문장을 만든 사례가 0건이다.
4. 검색 품질 기준과 허용 오탐·미탐 수치를 팀이 별도 합의하고 평가 기록을 남긴다.
5. 동일 모델 리비전·청킹·`top-k`·임계값으로 재실행 가능하며 CI와 MySQL PoC가 통과한다.

### 생성 연결 승인

- 승인일: 2026-09-10
- 승인자: 이희진 (전 영역 최종 리뷰어)
- 대상 평가 checksum: 0a6c9161d77a65dbf860c3d4d7eaf9c0efe5ee768bced68db514f5716da87bb5
- 고정 파라미터: 임베딩 모델·리비전, 현재 청킹, top-k=3, min_similarity=0.72
- 문턱 조건: 2·3·5(재현)은 scripts/key82_rag_evaluate.py `passed=true`
  (unsafe_context_entries=0, admission_accuracy=1.0)로 충족. 1·4는 평가셋
  (docs/data/key82-rag-poc-evaluation.json)과 PASS_CRITERIA를 검토·합의함.
- 판정: **생성 연결 허용.** GuideService에 KEY-276 검색 연결 가능(KEY-277 범위).
  ChatbotService·환자 화면 직접 연결은 KEY-96 계약대로 승인 GuideSection만 사용(불변).
- 재승인 조건: 평가셋·청킹·top-k·임계값 변경으로 checksum이 바뀌면 이 승인은
  자동 무효. 재평가·재승인 전까지 admit_generation_context는 다시 GENERATION_BLOCKED.

## 7. 전용 벡터 저장소 전환 기준

아래 중 하나가 동일한 Pilot 부하에서 7일 연속 발생하면 pgvector·Qdrant 비교 PoC를 별도 일감으로 연다.

- 병원당 검색 가능 승인 청크가 50,000개를 넘는다.
- 후보 조회 + Python cosine 검색 p95가 200ms를 넘는다.
- 후보 벡터 전송량이 요청당 10MB를 넘는다.
- 동시 검색 20건에서 API p95 500ms 또는 오류율 1%를 넘는다.

전환 시에도 승인 상태·현재 버전·출처·병원 격리는 MySQL을 정본으로 유지한다. 벡터 저장소는
검색 인덱스이며 승인 정본이 아니다. 색인 지연 또는 불일치가 있으면 검색을 차단한다.

## 8. 후속 일감 입력·출력

### 승인 지식 적재·색인 파이프라인

- 입력: 허용 출처 원문, 출처·이용조건·검토 메타데이터, 병원 범위
- 출력: 승인 전 문서 버전과 청크, 384차원 임베딩, checksum, 색인 리비전
- 금지: 수집 즉시 승인, 원문 공개, 병원 범위 누락

### 안내문 RAG 생성·근거 검토 연결

- 입력: 구조화 처방, 허용 섹션, 병원 범위, 승인·현재 청크 검색 결과
- 출력: 근거 청크 ID·문서 버전이 붙은 안내 초안 또는 안전 차단 코드
- 금지: 근거 없는 보완, 충돌 무시, 의사 승인 전 환자 노출
