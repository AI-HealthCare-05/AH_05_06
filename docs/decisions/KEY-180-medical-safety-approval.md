# KEY-180 처방약별 주의·응급 문구 의료 안전 기준·근거·승인 규칙 결정 기록

상태: **2026-08-25 결정 완료 — KEY-165 구현 기준**

## 목적

처방약별 안내 생성에 사용할 주의(`caution`)·응급(`emergency`) 문구의 의료 안전 기준과 근거·승인 규칙을 구현 전에 확정한다. 무엇을 구현할지가 아니라 KEY-165 구현자가 추가 의료 정책을 임의로 결정하지 않도록 입력·출력·예외를 정리하는 것이 이 문서의 역할이다.

- 부모: [KEY-75](https://leehee.atlassian.net/browse/KEY-75) LLM/RAG 안내 생성 공통 모듈 구현
- 구현 후행: [KEY-165](https://leehee.atlassian.net/browse/KEY-165) 처방약별 승인 주의·응급 문구와 근거 버전 관리
- 관련: KEY-5(의료 안전), KEY-82, KEY-83, KEY-84
- 발견: PR #100 / [KEY-161](https://leehee.atlassian.net/browse/KEY-161)

## 1. 처방약 식별·문구 매핑 단위

### 결정

매핑 단위는 **처방 세트(`prescription_set`)** 다. 개별 성분·제품명 단위 매핑은 이번 범위에 포함하지 않는다.

### 근거

- KEY-75가 이번 MVP를 "구조화된 처방 데이터 먼저, RAG는 나중"으로 이미 못박았다(1차 멘토링 근거). 성분 단위 동적 매핑은 사실상 근거 검색·조합이라 RAG류에 가깝다.
- `docs/decisions/KEY-163-ocr-real-contract.md`가 이미 `DIAGNOSIS + MEDICATION_NAME → 처방 세트 8종 중 매칭 → 안내 부품 조립` 흐름을 전제로 안내 생성을 설계했다. 매핑 단위를 성분으로 바꾸면 이 흐름과 어긋난다.

### 세트 밖 대증약물(소화제·감기약·진통제 "필요시" 등) 처리

`PrescriptionItem`은 이미 처방 하나에 약이 여럿 있는 것과, 기간 없는 "필요시" 약(`AS_NEEDED`)을 모델링하고 있다(`app/models/prescriptions.py`). 즉 주 치료제(세트 매칭 대상) 외에 환자 요청으로 얹는 대증약이 함께 처방되는 상황은 이미 데이터 구조가 예상한 패턴이다.

이런 대증약은 8종 세트 어디에도 속하지 않으므로 4절의 "미등록 약물"에 해당하지만, 그 원칙을 "안내 생성 자체를 막는다"는 뜻으로 적용하지 않는다.

- 세트 밖 대증약물에는 **개별 caution/emergency 문구를 만들지 않는다.**
- 대신 지금 이미 있는 **범용 caution 문구**(`app/services/guides.py`의 현재 `caution` 생성 문구 — "안내받지 않은 증상이나 불편감이 나타나면 의료진에게 알려 주세요")로만 커버한다. 이 문구는 애초에 어떤 약물·증상도 특정하지 않도록 설계되어 있어 안전하게 재사용할 수 있다.
- 소화제·감기약처럼 자주 쓰는 대증약에 개별 caution이 실제로 필요한지는 별도의 의료 판단이 필요하며, 이번 KEY-180 범위 밖이다. 필요하면 "공통 대증약물 카탈로그" 신설을 별도 Jira 일감으로 분리한다(신설 시 KEY-2/KEY-5 오너와 사전 합의 필요 — `docs/project_workflow.md` §3).

### KEY-165 인계 조건

- `catalog.py`에 `PrescriptionSet` 표(사전 등록, id 보유)를 신설해야 한다. 지금 `prescription.prescription_set`은 텍스트 스냅샷이라 FK가 없다(`app/models/prescriptions.py:59-69` 주석 — "템플릿 표가 생기면 그때 FK를 더한다"가 이 시점이다).
- 세트에 없는 처방 항목(대증약 등)은 caution/emergency 매핑 대상에서 제외하고 범용 문구만 적용한다. 별도 카탈로그를 새로 만들지 않는다.

## 2. 허용 근거 범위·등급

### 결정

Notion "의학지식 출처 관리" DB의 **A등급 자료만 caution/emergency 단독 근거로 허용**한다.

| 등급 | 처리 |
|---|---|
| A 핵심 | 단독 근거로 사용 가능 |
| B 보조 | 표현을 다듬는 보조 자료로만 사용. 단독 근거 불가 |
| C 검토·평가 | 이번 범위에서 사용하지 않음(RAG 후보 자료, 범위 밖) |
| 이용조건 미확인(`이용조건 확인 = NO`) | 사용하지 않음 |

### 이번 KEY-165에 쓸 수 있는 A등급 의약품 자료 (2026-08-25 기준)

| 자료명 | 발행기관 | 활용범위 |
|---|---|---|
| 의약품안전나라 제품 허가사항 | 식품의약품안전처 | 효능·효과, 용법·용량, 사용상 주의사항, 성분 |
| DUR 품목정보 Open API | 식품의약품안전처 | 병용·임부·연령 금기, 용량·기간 주의, 중복 정보 |
| DUR 성분정보 Open API | 식품의약품안전처 | 성분 기준 병용·임부·연령 금기 및 주의정보 |

### 근거

- 이미 팀이 등급 체계를 Notion DB로 관리 중이라 새 기준을 만들 필요가 없다. 식약처 발행·이용조건 확인 완료 자료로 한정하면 "공신력 있는 근거"라는 인수조건을 가장 보수적으로 만족한다.

## 3. 근거 기록 필수 메타데이터·승인 상태

### 결정

Notion DB 스키마를 그대로 채택하고, 승인 상태 값을 더한다. caution/emergency 문구 한 건마다 아래를 기록한다.

| 항목 | 대응 Notion 칼럼·값 |
|---|---|
| 출처 식별정보 | 자료명, 발행기관, 출처 링크 |
| 확인일 | 최종 검토일 |
| 버전 | 버전·기준일 |
| 등급 | 등급 |
| 승인 상태 | 초안 / 승인 / 폐기 3단계(정확한 이름은 KEY-165 구현 재량) |

- **승인 권한자**: 의료 안전 검수 책임자(이희진)가 "승인" 전환을 확정한다. 데이터 계약·모델 구조는 기술 리드(한금준)가 함께 검수한다. 새 절차를 만드는 것이 아니라 `docs/project_workflow.md` §3 공통 모듈 오너십 표("프롬프트·의료 안전·요구사항 → 의료 안전 검수 책임자 지정")를 그대로 적용하는 것이다.
- **현재 버전 판정 기준**: 같은 세트·섹션(`caution`/`emergency`)에 "승인" 상태 문구는 항상 하나뿐이다. 새 버전이 승인되면 이전 버전은 같은 트랜잭션에서 "폐기"로 바뀐다. 실제 안내 생성은 "승인" 상태 문구만 사용한다(4절 차단 원칙과 연결).
- **"하나뿐"은 DB로 강제한다**: 이 저장소의 다른 "하나뿐" 규칙(`(ocr_job, document_id)`, `(guide_document, section_key)` 등)은 모두 무조건 유니크 제약이지만, 이번 것은 "승인 상태일 때만 하나"인 조건부 제약이다. MySQL 8.0은 부분(조건부) 유니크 인덱스를 지원하지 않아 `unique_together`로 표현할 수 없다. 앱 트랜잭션만으로는 승인이 둘 남는 경합을 막지 못하고, 그러면 어느 문구가 나갈지 비결정적이 된다. nullable `approved_key`(예: `f"{세트}:{섹션}"`) 같은 칸을 두고 **승인 상태일 때만** 값을 채워 유니크 인덱스로 강제한다 — 유니크 인덱스는 `NULL`을 여럿 허용하므로 이 모양이면 표현된다.

KEY-165 구현자는 이 다섯 항목을 담을 자리와 위 유니크 제약을 새 모델(또는 `catalog.py`의 `PrescriptionSet` 관련 표)에 반드시 포함해야 한다.

## 4. 미등록·미승인·근거 누락 시 차단 원칙

### 결정

`docs/qa/KEY-33-synthetic-data-safety-checklist.md`의 `MED-01`, `MED-06` 원칙을 정식 정책으로 확정한다.

- **세트에 등록되지 않은 약물**: 그 약물에 대한 개별 caution/emergency 문구를 만들지 않는다. 빈칸도 추측하지 않는다(`MED-01`).
  - 단, 1절에서 정한 대로 **세트 밖 대증약물**은 이 원칙의 적용 대상이지만 "안내 생성 자체를 막는다"는 뜻이 아니다. 해당 진료의 안내문 생성은 정상 진행하고, 그 약물만 개별화하지 않은 채 범용 caution 문구로 커버한다.
- **승인되지 않은 새 조합**: 자동으로 새 세트를 만들거나 승인하지 않는다. 새 세트 등록이 필요하다는 사실만 표시하거나 로그로 남긴다(`MED-06`).
- **근거 누락 문구**: 2·3절의 근거·메타데이터 요건을 만족하지 못한 caution/emergency 문구는 생성에 사용하지 않는다.

### 근거

- 이미 팀이 합의해 QA 문서에 적어 둔 원칙이라 재논의가 아니라 확정이다. 1절에서 다룬 대증약물 예외만 이번에 명시적으로 추가한다.

## 5. `caution` 편집 가능 / `emergency` 잠금

### 결정

현재 구현·정책을 그대로 유지한다. **변경 없음.**

- `caution.locked = false` — 의사가 환자 상태에 맞춰 고칠 수 있다.
- `emergency.locked = true` — 식약처 의약품정보 기준 응급 문장이며 수정·완화·삭제할 수 없다. `PATCH .../sections/emergency`는 `409 SECTION_LOCKED`.

### 근거

- `app/models/visits.py`의 `GuideSectionKey`·`GuideSection.locked`, `docs/api/hospital.md` §5, KEY-161이 이미 구현·문서화·병합을 완료했다. KEY-180은 이 정책을 뒤집지 않는다는 것을 재확인만 한다.

## 6. 신규 버전의 소급 적용 금지

### 결정

새 caution/emergency 버전이 등록되어도 **이미 승인된 안내문의 본문과 근거 버전은 바뀌지 않는다.**

### 근거·구조적 보장

- `GuideSection.generated_body`는 안내 생성 시점에 문구를 **복사**해서 저장하고, 마스터 콘텐츠 표를 실시간 참조하지 않는다(`app/services/guides.py`의 `generate()` — 각 섹션을 `GuideSection.create(...generated_body=...)`로 값 자체를 그대로 저장). 마스터가 나중에 바뀌어도 이미 만들어진 `GuideSection` 행은 자동으로 바뀌지 않는다.
- 이 복사 방식은 이미 존재하는 아키텍처 특성이라 새로 설계할 필요가 없다.

### KEY-165 인계 조건

- 새로 만들 caution/emergency 마스터 콘텐츠 표도 이 "생성 시점 복사" 패턴을 그대로 따른다.
- 어느 버전의 근거를 썼는지 추적할 수 있도록, `GuideSection` 또는 별도 이력 표에 **근거 버전 식별자**(2·3절 메타데이터 중 최소 "버전·기준일" + "출처 링크")를 함께 남긴다. 지금은 emergency 문구를 어떤 근거로 만들었는지 추적할 자리가 없다 — 이번 결정으로 새로 요구되는 것이다.
- **근거 버전은 `generated_body`를 설명하지 `edited_body`를 설명하지 않는다.** `caution`은 의사가 `edited_body`로 고칠 수 있고 환자는 `GuideSection.body`(있으면 `edited_body`, 없으면 `generated_body`)를 읽는다(5절). 의사가 고친 `edited_body`는 의료진의 판단이지 근거가 뒷받침하는 문장이 아니므로, 근거 버전 추적 표는 자신이 어느 쪽(`generated_body`)을 설명하는지 구분해서 남긴다.

## KEY-165 구현 인계 조건 요약

구현자가 추가로 임의 결정하지 않도록, 위에서 정한 인계 조건만 모은다.

1. `catalog.py`에 `PrescriptionSet` 표(사전 등록, id 보유)를 신설한다. `prescription.prescription_set`은 여전히 스냅샷 문자열로 남기고, 새 표는 별도로 둔다(진료 시점 스냅샷 원칙은 KEY-137 결정을 따른다).
2. 세트별 caution/emergency 문구는 A등급 근거만 단독 근거로 쓰고, 근거 식별정보·확인일·버전·등급·승인 상태를 함께 저장한다(3절 표).
3. 같은 세트·섹션에 "승인" 상태 문구는 항상 하나만 존재해야 하며, 새 버전 승인 시 이전 버전은 자동으로 "폐기"로 전환한다. 이 제약은 앱 트랜잭션이 아니라 nullable `approved_key` 등을 이용한 DB 유니크 인덱스로 강제한다(3절).
4. 세트 밖 대증약물(소화제·감기약 등)은 이번 범위에서 개별 매핑 대상이 아니다. 별도 카탈로그를 새로 만들지 않는다(1절).
5. 미등록 약물·미승인 조합·근거 누락 문구는 생성에 사용하지 않되, 안내 생성 자체를 막지 않는다(4절).
6. `caution`은 `locked=false`, `emergency`는 `locked=true`를 유지한다(5절, 변경 없음).
7. 새 마스터 콘텐츠는 생성 시점에 안내문에 복사되고, 어느 근거 버전을 썼는지 추적 가능해야 한다. 근거 버전은 `generated_body` 기준이며 의사가 고친 `edited_body`와는 구분한다(6절).
8. 실제 환자정보·운영 비밀값을 사용하지 않는다.
