# KEY-119 진료 관계 변경 잠금 결정 기록

상태: **2026-08-24 리뷰 합의 완료 — v1 구현 기준**

## 목적

OCR 또는 승인 안내가 연결된 뒤 진료의 식별 관계가 바뀌어 의료문서·안내와 진료 정보가 어긋나는 것을 막는다. 큰 API 계약 변경은 구현 전에 공유하고 합의한다는 프로젝트 규칙에 따라, 아래 정책을 코드보다 먼저 확정했다.

## 구현 전 출발점

PR #69(KEY-135)에서 다음 동작이 `develop`에 병합됐다.

- `department_id`가 PATCH 본문에 있으면 잠금 여부를 먼저 확인한다.
- 상태와 무관하게 `OcrJob`이 하나라도 연결되어 있으면 `409 VISIT_LOCKED`다.
- 안내 상태가 `APPROVAL_PENDING` 또는 `SCHEDULED_TO_SEND`이면 `409 VISIT_LOCKED`다.
- `department_id: null`도 `department` 스냅샷 삭제이므로 잠금 대상이다.
- 타 병원 진료는 잠금 여부를 노출하지 않고 `404 VISIT_NOT_FOUND`다.
- `visit_summary`, `doctor_note`, `status`, `planned_stop`은 잠기지 않는다.

## 확정 정책

| 항목 | 현재 동작 | 제안 | 합의 |
|---|---|---|---|
| `department_id` | 잠금 | 그대로 유지 | 잠금 |
| `doctor_id` | 잠기지 않음 | 식별 관계로 보고 함께 잠금 | 잠금 |
| `visited_at` | 잠기지 않음 | 식별 관계로 보고 함께 잠금 | 잠금 |
| `visit_summary` | 잠기지 않음 | 비잠금 유지 | 비잠금 |
| `doctor_note` | 잠기지 않음 | 비잠금 유지 | 비잠금 |
| `status` | 잠기지 않음 | 비잠금 유지 | 비잠금 |
| `planned_stop` | 잠기지 않음 | 비잠금 유지 | 비잠금 |
| OCR 잠금 시점 | 모든 `OcrJob` 존재 즉시 | 처리 중·완료 데이터 보호, 실패 작업의 영구 잠금 방지 | `PROCESSING`, `COMPLETED`만 잠금 |
| 같은 값 재전송 | 필드가 본문에 있으면 차단 | 실제 관계 변경만 차단 | 동일값 허용 |

`FAILED` OCR은 처리와 보호할 결과가 끝난 상태이므로 단독 잠금 근거에서 제외한다. 재시도하면 새 `PROCESSING` 작업이 만들어져 즉시 다시 잠긴다. 현재 상태 enum에는 `CANCELLED`가 없으며, 취소 상태가 추가될 때 잠금 제외 여부를 별도 계약으로 확정한다.

`patient_id`는 `VisitUpdateRequest` 필드가 아니고 추가 입력도 금지되어 공통 `400 INVALID_REQUEST`로 거부된다. 애초에 PATCH로 바꿀 수 없는 관계이므로 잠금 대상 표에 포함하지 않는다.

## 구현 후 반드시 고정할 회귀 시나리오

- 미연결 진료에서 확정된 잠금 대상 필드 수정 허용
- OCR 연결 뒤 잠금 대상 필드 각각 `409 VISIT_LOCKED`
- 승인 안내 연결 뒤 같은 잠금 규칙 적용
- 비잠금 대상 필드는 연결 뒤에도 수정 가능
- `department_id: null` 스냅샷 삭제 정책 유지
- 타 병원 진료는 `404 VISIT_NOT_FOUND`
- 응답과 로그에 OCR 원문·승인 안내 본문·환자 실데이터·토큰 원문 미노출

## 합의 근거

- 리뷰어 이희진: 잠금·비잠금 필드, `FAILED` 제외, 동일값 허용 확정
- OCR 연결 조건 협의자 한금준: `OcrJob` 생성 시점 잠금 유지 및 실패·취소 작업 검토 제안
- PR #98의 합의 내용을 서비스·API 문서·회귀 테스트에 동일하게 반영한다.
