# KEY-323 생활관리(life) 섹션 근거 출처 결정

상태: **코드 착수 전**
상위: KEY-75 · 관련: KEY-82, KEY-276, KEY-277, KEY-283, KEY-161
담당: 한금준 · 리뷰어: 이희진, 권일준

## 1. 결론

- 생활관리 섹션은 **PCOS만 RAG 검색 대상**으로 삼는다. 자궁내막증은 청크·임베딩을 만들지 않고
  고정 템플릿으로 간다(§3).
- 새 출처를 추가로 늘리는 판단 기준(2026-09-10, 이희진): **출처 추가로 얻는 이득 < RAG 복잡도
  상승**이면 추가하지 않는다. 다출처 병합보다 스코핑이 확실한 소수 출처를 우선한다.
- PCOS는 **Monash 가이드라인 v1(Figshare, CC BY 4.0) PDF p35~38**을 근거로 쓴다(§2). 한때
  JCEM 저널판으로 정했다가 라이선스 문제로 되돌렸다 — 그 경위를 아래에 남긴다. 같은 실수를
  반복하지 않으려면 왜 되돌렸는지가 근거보다 중요하다.
- EC2에 이미 적재된 PCOS 지식(JCEM 기준, document `9596c6d9…`, 191청크, `DRAFT`)은 **승인하지
  않고 폐기**한다. Monash v1 p35~38로 새로 적재한다.
- 자궁내막증은 ESHRE 학술판(Human Reproduction Open) 기반 **고정 템플릿**이며, 청크는 없지만
  출처 추적을 위해 `KnowledgeDocument` 레코드는 만들고 `APPROVED`로 둔다(§3).
- 진행 순서는 **코드(한금준) → 폐기·재적재(권일준) → 검토·승인(이희진)**이다(§5). 이 문서
  작성 시점에 코드 착수 전이다.

## 2. PCOS — 저널판에서 Monash판으로 되돌린 경위

### 2.1 처음 선택 (2026-09-11, 이희진 결정)

JCEM 108(10):2447-2469 (PMC10505534, CC BY-NC 4.0, 23p, 로컬 `다낭성난소증후군.pdf`
md5 `b7713416…`)로 정했다. 이유는 섹션 3이 권고 표로 정리돼 있어 스코핑이 쉬워 보였기
때문이다. Monash 원본 PDF(`_full.pdf`, 로컬 보관)는 그 시점에 내부 저작권 페이지의
"unaltered form only" 문구만 보고 부적합으로 오판했다가, Figshare 등재 레코드
(DOI `10.26180/24003834.v1`, license **CC BY 4.0**, md5 `75bb8757…`가 적재본과 일치)를
확인하고 정정했다 — 라이선스는 **PDF 내부 문구가 아니라 등재 레코드까지 확인**해야 한다.
그럼에도 저널판(CC BY-NC, 라이선스가 더 좁음)으로 갔던 건 상업화 여지보다 스코핑 편의를
우선한 결정이었다.

### 2.2 2026-09-13 승인 사전검토에서 전제가 깨짐

- JCEM판의 실제 권고 31개는 본문이 아니라 **Table 4** 안에 있는데, 표 끝(PDF p18) 주석에
  "© Monash … by permission … **not covered by the terms of the Creative Commons licence**,
  contact the rights holder"라고 적혀 있다. 즉 **저널판의 CC BY-NC로는 정작 쓰려던 섹션 3
  권고를 쓸 근거가 없었다** — 논문 전체 라이선스와 표 하나의 라이선스가 다른 경우였다.
- 게다가 JCEM p10(2.6.3~2.8, 항우울제 권고 3.6k자)과 p12(4.1, 약물 원칙 1.1k자)가 섹션
  경계에서 서로 섞여 있어 페이지 범위로 스코핑하는 것 자체가 불가능했다(텍스트 경계로
  잘라야 하는데, 그러면 위 라이선스 문제와 별개로 구현이 더 복잡해진다).
- 반면 Monash v1(Figshare 레코드, CC BY 4.0 재확인)은 **PDF p35~38이 정확히 섹션 3 권고
  31개**다(p34 끝=2.8, p39 시작=4장, 약물 언급 0건) — 페이지 범위만으로 깔끔하게 스코핑된다.
- 비교 참고: ESHRE Human Reproduction Open PDF에는 이런 "CC 제외" 주석이 없다 — 표·본문
  라이선스가 갈리는 게 일반적인 일은 아니고, 이번 건은 반드시 개별 확인해야 하는
  사례였다는 뜻이다.

**결론: Monash v1 p35~38로 복귀한다.** 잔여 위험 하나는 남아 있다 — Monash PDF p2에
"all rights reserved / unaltered form only" 문구가 있어 Figshare 레코드 라이선스와
불일치한다. 이전 결정대로 **등재 레코드를 우선**한다(§2.1과 같은 원칙).

### 2.3 2026-09-13 추가 확인 — Monash 개정판과의 관계

Monash가 2026-05-12에 PCOS를 **PMOS**로 개명했고, 2026-06-11에 개정 PDF(274p, **CC 레코드
없음, 저작권 문구만**)를 공개했다. 개정본 자체가 "관리 방식은 바뀌지 않았고, 권고는
PMOS/PCOS로 용어만 바뀌었다"고 명시한다. 개정본 섹션 3(p39~42)을 PMOS/PCOS→PCOS로
정규화한 뒤 v1 p35~38과 대조해 **완전히 일치**함을 확인했다. 따라서 **CC BY 4.0인
Figshare v1을 그대로 근거로 쓰는 게 맞다** — 개정판(라이선스 없음)을 쓸 이유가 없다.

**주의: 개정판을 내려받지 말 것.** Monash 사이트에서 새로 검색하면 개정판(274p, PMOS,
라이선스 없음)이 먼저 나올 수 있다. 반드시 로컬에 보관된 v1 파일(`_full.pdf`,
md5 `75bb8757…`)을 사용한다. 서비스 화면의 질환명 표기(PCOS vs PMOS)를 어떻게 할지는
이 결정과 별개로 정한다 — 여기서는 근거 출처만 다룬다.

### 2.4 적재·승인 처리

- EC2에 이미 있는 PCOS 지식(JCEM 기준, document `9596c6d9…`, 191청크)은 `DRAFT`다. **승인하지
  않고 폐기**한다. `stable_source_key`가 `source_url`을 포함하므로 Monash v1은 URL이 달라
  **새 document**로 적재된다 — 기존 문서를 고쳐 쓰는 게 아니다.
- 현재 적재 스크립트는 **적재와 같은 실행에서만 승인**(`approve:true` + `--approved-by`)
  가능하다. 적재해 둔 draft를 나중에 검토한 뒤 `version_id`로 승인하는 경로가 없다 —
  이번 KEY-323 코드 요청에 포함한다(§4).
- `approve()`는 같은 document의 **이전 승인 버전만** `DEPRECATED`로 바꾼다. document 자체를
  단독으로 폐기하는 경로는 없다 — JCEM `9596c6d9…` 폐기를 위해 이 경로도 §4에서 같이
  만든다.
- KEY-276 개발 중 9/8 적재·9/9 승인 기록(5건)은 **로컬 실행**(`DB_HOST=127.0.0.1`)이라 실행
  담당자 로컬 DB의 것이다. 이희진 로컬에는 0건 — 즉 이 5건은 EC2/Pilot 상태와 무관하다.
- `app/Dockerfile`에는 `scripts/`와 `sentence-transformers`가 없어 EC2 `fastapi` 컨테이너에서
  직접 적재할 수 없다. **배포·적재 담당은 권일준**이다.
- EC2 지식 테이블이 이미 비어 있지 않다면 raw SQL로 지우지 않는다 — deprecate/폐기 경로를
  코드로 만들어 그걸로 처리한다.

## 3. 자궁내막증 — RAG 청크 없음, 고정 템플릿

ESHRE 학술판(Human Reproduction Open, **CC BY-NC 4.0** — PCOS 저널판과 라이선스 종류는
같지만, 여기서는 청크·임베딩을 만들지 않으므로 §2.2의 "표만 CC 제외" 같은 문제와는
무관하다) 기반. 안내에 실제로 들어갈 템플릿 전문은 티켓 §4 확정본을 그대로 쓴다.

- **KnowledgeChunk·임베딩은 미생성. 단 `KnowledgeDocument` 레코드는 생성하고 `APPROVED`로
  둔다.** 이유: (a) KEY-277·KEY-314의 의사 화면 근거 표기가 스냅샷 필드와 형식을 맞춰야
  하고, (b) 지침이 개정되면 확인일·버전을 추적할 지점이 필요하며, (c) KEY-283 등급(A) 기록
  자리가 있어야 한다.
- 쓸 수 있는 근거는 **②비약물중재 GPP**, **③암예방 수칙 GPP** 둘뿐이다. 둘 다 원문이
  "women with endometriosis"를 대상으로 한다.
- **①"healthy lifestyle·절주·운동"(weak 권고)은 미사용** — 원문이 "preventing
  endometriosis in the future"를 대상으로 해서, 이미 진단받은 환자가 아니라 1차 예방
  대상용 문구다. §4의 함정과 같은 종류의 오독 위험이라 별도로 걸러냈다.
- 이희진 결정: ③의 **암 맥락은 화면에 노출하지 않는다**, "자외선 차단"은 제외한다, 응급·주의
  문구는 KEY-161 경계이므로 이 섹션에 포함하지 않는다.

## 4. 반복된 함정 — 원문의 적용 대상 확인

생활관리 문구는 겉보기와 달리 **원문이 귀속시킨 적용 대상(환자군·병형)이 다른 경우가
많다.** 이번 작업에서 두 번 걸렸다:

- 국가건강정보포털 「생리통」 문구는 전부 **「일차 생리통」** 소속인데, 자궁내막증은
  **이차 생리통**이다 — 겉으로는 관련 있어 보이지만 대상이 다르다.
- ESHRE ①("healthy lifestyle") 권고는 **1차 예방**(병이 생기기 전) 대상이다 — 자궁내막증
  환자 대상 생활관리로 오인하기 쉽다(§3).

**대응: 요약 도구(WebFetch 등) 말고 `curl` 등으로 원문을 직접 확인**하고, 그때마다
"이 문구가 실제로 누구를 대상으로 한 권고인가"를 확인한다. 이 확인 절차를 KEY-323
인수조건에 포함한다.

## 5. 진행 순서와 코드 요구사항

**순서: 코드(한금준) → 폐기·재적재(권일준) → 검토·승인(이희진).** 이 문서 작성 시점에
1단계도 착수 전이다.

코드 요구사항 4가지:

1. **페이지 범위 스코핑** — Monash v1 PDF의 p35~38만 추출·청킹 대상으로 삼는다.
2. **draft 폐기 경로** — document 단독을 폐기할 수 있는 경로. JCEM `9596c6d9…`에 사용한다.
3. **레코드 전용 근거** — 청크·임베딩 없이 `KnowledgeDocument`만 만들고 승인하는 경로.
   자궁내막증(§3)에 사용한다.
4. **적재와 분리된 사후 승인 명령** — 지금은 적재 시점에만 승인 가능하다. draft로 적재해
   두고 나중에(권일준 재적재 → 이희진 검토 이후) `version_id`로 승인하는 명령이 필요하다.

Aerich 마이그레이션 정합성 이슈는 KEY-323에 포함하지 않는다 — KEY-333(KEY-216 하위, 권일준
권장 담당)에서 별도로 다룬다.

## 8. KEY-277과의 관계

KEY-277(승인 지식 기반 안내 생성)은 이 문서와 무관하게 이미 코드가 완성돼 병합 대기
중이다. `GUIDE_RAG_ENABLED`는 기본값 `false`라 KEY-323 완료 여부와 무관하게 KEY-277을
병합해도 기능은 켜지지 않는다. 이 문서가 막는 것은 KEY-277의 Pilot 수동 시나리오 8종 중
"정상"(PCOS 근거로 실제 RAG 생성) 1건뿐이다 — 코드가 아니라 실측할 승인된 콘텐츠가
없어서다. §5가 끝나면 그 1건을 마저 확인하고, 그 뒤에 `GUIDE_RAG_ENABLED=true` 활성화
여부를 별도로 판단한다.
