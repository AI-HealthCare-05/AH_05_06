# 인프라 두 그림 비교 — 우리는 어디까지 필요한가

> 팀이 공유한 아키텍처 두 장을 우리 규모에 대어 본 문서.
> 짝 문서 — [`spec-ai-worker.md`](spec-ai-worker.md) 워커 연동 · [`spec-medical.md`](spec-medical.md) 발송 스케줄
> **결론부터 — 그림 ①로 만들고, 그림 ②에서 셋만 가져온다.**

---

# 1. 두 그림은 같은 구조의 두 단계다

| | **① EC2 한 대** | **② AWS 관리형** |
|---|---|---|
| 실행 | `docker compose` | **ECS** — 웹은 Fargate · 워커는 EC2 |
| 앞단 | Nginx | **Route 53 + ALB** |
| Redis | 컨테이너 | **ElastiCache** |
| DB | 컨테이너 `mysql` | **RDS MySQL** |
| 확장 | 손으로 | **Auto Scaling** — 큐 적체 기준 |
| 저장소 | S3 | S3 + **EFS** |
| 학습 | 워커가 겸함 | **별도** — AWS Batch / EC2 Spot |
| CI/CD | 없음 | GitHub Actions → ECR → ECS |
| 관측 | 없음 | CloudWatch · X-Ray · SNS |

**핵심 아이디어는 같다** — 웹과 AI를 갈라 두고 Redis로 잇는다. 바뀐 것은 **누가 운영하느냐**(직접 → AWS)와 **어떻게 늘리느냐**(손 → 자동)뿐이다.

## 큐 방식 — Redis Stream으로 정해져 있다 ✅

그림 ②는 큐 이름이 `ai_task_queue` / `ai_processing_queue`라 List 두 개(`BRPOPLPUSH`) 패턴처럼 보이지만, **부트캠프 「프로젝트 아키텍처 설계」 가이드가 Redis Stream을 명시한다.**

> **왜 Redis Stream인가?**
> **영속성** — 서버가 잠시 꺼져도 작업 내역이 사라지지 않는다.
> **상태 관리** — 어떤 워커가 어떤 작업을 가져갔는지, 성공했는지 실패했는지(`XACK`, `XCLAIM`)를 체계적으로 관리할 수 있다.

가이드의 데이터 흐름도 우리 설계와 같다 — `XADD` → 접수 응답 → 워커가 소비 → `XACK` + **Publish** → FastAPI가 **Pub/Sub 구독** → **SSE로 전송**.

**[`spec-ai-worker.md`](spec-ai-worker.md)가 이 기준으로 쓰여 있다.** 고칠 것이 없다.

# 2. 우리 규모 — 숫자로

명세와 화면에 이미 답이 있다.

| | 근거 |
|---|---|
| 의원 | **하나** |
| 하루 진료 | **10~30건** — `S1` 목록 예시가 작성 중 1 · 보완 1 · 승인 요청 3 · 발송 대기 1 · 완료 2 |
| 월 문자 | **약 1,000통** — `A1-4` 발송량 예시 · 환자 1명당 3~5통 |
| 동시 사용자 | **스탭 1~2 + 의사 1** — 접수대에 앉은 사람 수만큼 |
| 판독 요청 | 하루 10~30회 · **한 건에 이미지 2~3장** |

## 이 숫자가 뜻하는 것

```
하루 30건 × 판독 30초  =  하루 15분
워커 하나의 가동률       ≈  1%
```

**Auto Scaling이 조절할 것이 없다.** 큐가 쌓이려면 요청이 처리 속도보다 빨라야 하는데, 우리는 **스탭이 손으로 업로드하는 속도**가 상한이다. 한 사람이 30초에 한 건씩 올려도 워커 하나가 따라잡는다.

문자도 마찬가지다 — **하루 33통**은 API 호출 33회다.

# 3. 그래도 나눠야 하는 이유는 남는다

**규모 때문이 아니다.** 아래 셋은 하루 10건이어도 성립한다.

| | |
|---|---|
| **한 건이 오래 걸린다** | 판독 10~30초. FastAPI가 직접 하면 그 요청이 워커 프로세스를 물고 있어, `--workers 3`이면 **동시 셋이 한계**다 |
| **의존성 무게가 다르다** | `torch` + `sentence-transformers`는 수 GB. `app/Dockerfile`이 이미 `--group app --no-dev`로 빌드해 **웹 이미지에 안 넣는다** |
| **AI가 죽어도 웹은 살아야 한다** | 지금 `ai-worker`가 `Restarting`인데 Swagger는 200이다. 합쳐 두면 승인 화면도 같이 죽는다 |

**결론 — 컨테이너 분리와 Redis 큐는 필요하고, 관리형 서비스와 오토스케일링은 불필요하다.**

---

# 4. ②에서 가져올 것 셋

전부 버리지 않는다. 우리 규모에서도 값을 하는 것이 셋 있다.

## ① S3 — 진료기록 사진

**TTL 72시간을 직접 짜지 않아도 된다.** S3 라이프사이클 규칙 한 줄이면 명세의 「72시간 뒤 저절로 사라진다」가 성립한다. EC2 로컬 디스크에 두면 그 배치를 직접 만들고, 워커가 여럿이면 어느 디스크에 있는지도 관리해야 한다.

> **버킷은 비공개 · 서버 사이드 암호화 · 프리사인드 URL 전제다.**
> 이 사진은 실제 환자의 EMR 캡처이고 제3자 실명이 섞일 수 있다. 두 그림 다 그 부분이 안 그려져 있다.

## ② DB 백업 — RDS 또는 그에 준하는 것

**이건 규모 문제가 아니라 데이터 성격 문제다.**

컨테이너 `mysql`은 EC2 인스턴스가 죽으면 **같이 죽는다.** 우리가 들고 있는 것은 **진료 기록과 안내문**이고, 명세는 「삭제하지 않는다 · 계속 보관한다」다. 유실되면 되돌릴 방법이 없다.

| 고를 수 있는 길 | |
|---|---|
| **RDS MySQL** | 자동 백업 · 특정 시점 복원이 기본. 값은 더 든다 |
| EC2 + EBS 스냅샷 | 싸다. 대신 스냅샷 주기와 복원 절차를 직접 만들어야 한다 |
| 컨테이너 mysql만 | **권하지 않는다** — 인스턴스와 운명을 같이한다 |

## ③ CI/CD

**이미 반쯤 있다.** `.github/workflows/checks.yml`이 ruff · mypy · 테스트를 돌린다. 여기에 **배포**를 잇는 것은 어렵지 않고, 손으로 ssh 붙어 `docker compose up`을 치는 것보다 안전하다.

---

# 5. 안 가져올 것

| | 왜 |
|---|---|
| ECS / Fargate | 컨테이너 한 벌을 EC2 한 대에서 돌리는데 오케스트레이터가 필요 없다 |
| ALB + Route 53 | **Nginx가 같은 일을 한다.** `infra/nginx/`에 설정이 이미 있고 `scripts/certbot.sh`로 HTTPS도 된다 |
| ElastiCache | Redis 컨테이너로 충분하다. 캐시가 날아가도 큐만 다시 채우면 된다 |
| **Auto Scaling Group** | **조절할 부하가 없다**(2장) |
| EFS | 워커가 여럿이 같은 파일을 봐야 할 때 쓴다. 우리는 S3로 족하다 |
| **학습 파이프라인** | **우리에겐 학습이 없다** — 추론 둘뿐이다(판독 · 조립) |
| **GPU(`g5`)** | 판독 엔진을 외부 API로 정하면 아예 불필요하다(7장) |

---

# 6. 두 그림 다 빠진 것 셋 ★

**이것이 이 문서에서 가장 중요한 부분이다.** 규모 논의보다 앞선다.

## ① 문자 발송이 없다

**우리 프로그램의 본체가 문자 발송이다.** 환자 한 명당 3~5통, 석 달에 걸쳐. 그런데 **두 그림 어디에도 문자 대행사 연동이 없다.**

`clinic.sender_number` · `sms_balance` · `message.status` 같은 표가 전부 이것을 전제하는데, 인프라 그림에는 나갈 통로가 안 그려져 있다.

## ② 스케줄러가 없다

| 돌려야 할 것 | 언제 |
|---|---|
| 진료 안내문 | 승인 뒤 지정 시각 (기본 오늘 18:00) |
| 확인 문자 | **D+7 · D+15 · D+30** |
| 소진 임박 | 소진 3일 전 |
| **이탈 판정 배치** | **하루 한 번** |

**Redis 큐는 「지금 처리할 것」이지 「3주 뒤에 보낼 것」이 아니다.** 예약 발송을 돌릴 자리가 필요하다 — `EventBridge Scheduler` · ECS Scheduled Task · 또는 컨테이너 안의 cron.

> **이 프로그램은 「한 번 보여주는 화면」이 아니라 「석 달에 걸친 발송」이다.**
> 그 석 달을 굴리는 부품이 인프라 그림에 없다.

## ③ SSE 경로

그림 ①엔 `SSE Response`가 명시돼 있는데 ②엔 없다. ALB는 SSE를 지원하지만 **idle timeout을 늘려야** 하고(기본 60초), Fargate task가 여럿이면 **결과를 받은 task와 SSE 연결을 든 task가 다를 수 있다.**

Redis **pub/sub**이면 모든 task가 구독하니 해결되는데, ②엔 pub/sub이 없고 큐 둘만 있다.

# 7. 결론

| | |
|---|---|
| **만드는 것** | **그림 ①** — EC2 한 대 + `docker compose`. `infra/docker/docker-compose.prod.yml`과 `scripts/deployment.sh`가 이미 준비돼 있다 |
| **가져올 것** | S3(사진 TTL) · DB 백업 · CI/CD |
| **문서·발표용** | 그림 ② — 「트래픽이 늘면 이렇게 확장한다」 |

**그림 ②를 버리는 것이 아니라 목표로 둔다.** 「지금은 ①이고, 늘면 ②로 간다」는 것 자체가 설계 판단이고, 발표에서 그렇게 설명하는 편이 「처음부터 ②를 만들었다」보다 낫다 — **규모에 맞는 선택을 했다는 근거**가 되기 때문이다.

## 정할 것

| # | 무엇 | 누가 |
|---|---|---|
| 1 | **문자 대행사와 발송 통로** — 두 그림 다 빠져 있다 | 팀 · 스탭 |
| 2 | **예약 발송·배치를 무엇으로** — cron / EventBridge / APScheduler | 팀 |
| 3 | **판독 엔진 — 외부 API냐 로컬 모델이냐** | 팀 · ②의 `g5`는 로컬 모델 전제다 |
| 4 | **DB 백업을 어떻게** — RDS / EBS 스냅샷 | 팀 |
| ~~5~~ | ~~큐 방식~~ | **닫힘 — Redis Stream**(가이드 명시) |

**1·2번이 가장 급하다.** 우리 프로그램이 실제로 하는 일이 거기 있는데 두 그림 다 그 자리가 비어 있다.

# 8. 가이드가 말하는 「설계의 이유」와 우리 규모

부트캠프 가이드는 아키텍처 설계의 목적을 이렇게 든다 — **안정성 · 확장성 · 성능 · 유지보수 · 보안 · 비용 효율.** 그리고 「**대규모 트래픽**을 처리하고 서비스 붕괴를 막는」 것이라고 적는다.

**우리에게 맞는 것과 아닌 것을 갈라 본다.**

| 가이드가 든 이유 | 우리에게 |
|---|---|
| 시스템 안정성 · 가용성 | **맞다** — AI가 죽어도 승인은 돌아가야 한다 |
| 유지보수 · 변경 용이성 | **맞다** — 6인이 갈래를 나눠 맡는다 |
| 보안 | **맞다** — DB를 내부에 두는 것. 우리는 **환자 자료**라 더 세다 |
| 성능 최적화 | **반쯤** — 응답 속도가 아니라 **한 건이 오래 걸리는 것**이 문제다 |
| **유연한 확장성** | **아니다** — 늘릴 부하가 없다(2장) |
| **비용 효율성** | **반대로 작용한다** — 관리형 서비스를 다 켜면 우리 규모엔 더 비싸다 |

**「대규모 트래픽」이 전제인 항목만 빼면 나머지는 그대로 우리 것이다.** 그래서 **분리는 하되 관리형·오토스케일링은 안 한다**는 결론이 나온다.
